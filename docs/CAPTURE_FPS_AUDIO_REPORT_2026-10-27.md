## 1. 屏幕捕获 60 帧只有 55 帧（日志 67）

### 结论

原因在 Windows 的 WGC，与游戏和 Veyra 的处理链无关。Windows 11 24H2 起，WGC 会话默认带 16 ms 的 `MinUpdateInterval`：离上一帧不到 16 ms 合成出来的帧会被直接丢掉。在 165 Hz 显示器上，16 ms 之后的下一次合成要到 18.18 ms（3 个刷新周期），所以 60 帧的窗口只能收到 165/3 = 55 帧。这个限制也让 120 帧上限形同虚设。Veyra 之前从没设置过这个属性。

### 证据

- **日志 67**：RTX 5090 D v2，164.991 Hz，HDR 开，没有 VRR。6 个不同的窗口目标，接收速率上限全部是 55.0 fps（330 个统计窗口中 179 个正好是 55）。重置时测到的帧间隔都是 18.18 ms 的 1、2、3 倍，一次也没出现 60 帧在 165 Hz 下应有的 12.12 ms。稳态时 Veyra 自己的限速器没有丢帧（`dropped` 计数不变）。
- **本机探针**（`scripts/acceptance/wgc-rate-probe.cpp`，320 Hz HDR，源窗口严格 60.00 fps）：

  | 最小更新间隔 | 未遮挡 | 被遮挡（相当于游戏模式） |
  | --- | --- | --- |
  | 默认 16 ms | 54.3–55.1 | 52.5–53.9 |
  | 1 ms | 60.2 | 60.3 |
  | 7.333 ms（修复后的取值） | 60.2 | 60.2 |

  另一个对照是“60 帧上限 + 游戏内垂直同步”的源，它本身就只有 53.3 fps。这是游戏一侧的另一种原因，与本问题无关。

- **真实程序端到端**（`scripts/acceptance/screen-capture-rate.py`，私有配置，窗口模式，无效果器）：

  | 程序 | 60 上限：接收 / 处理 | 120 上限：接收 / 处理 |
  | --- | --- | --- |
  | 2.1.1 正式版 | 53.55 / 53.55 | 53.72 / 53.72 |
  | 修复后 | 60.0 / 60.0 | 59.99 / 59.99 |

### 修改（`src/source/ScreenCaptureSource.cpp`）

1. **设置最小更新间隔**：每个 WGC 会话（打开、静止窗口重启、跟随显示器时刷新率变化）都设成“上限间隔的一半减 1 ms”，最少 1 ms。在任何刷新率网格上，不超过上限的源，相邻两次合成至少相隔半个上限间隔，所以一帧也不会丢。超过上限的帧仍由原来的累计期限限速器去掉。系统没有这个属性时不做任何改动。
2. **放宽限速器容差**：原来只接受比期限早 0.5 ms 以内的帧。桌面繁忙时，合成时间戳会晚一两个刷新周期，下一帧又准时到，结果 60 帧窗口在 60 上限下只处理了 58.1 帧。现在接受早到四分之一个间隔以内的帧，修复后为 60.0。累计期限仍保证平均帧率不超过上限（已用模拟核对）。
3. **缓存每秒一次的 HDR 检查**：这项检查原来每次都新建 DXGI factory 并遍历全部输出，在引擎线程上中位 0.43 ms，最长一次 21.8 ms。现在缓存 factory，只在 `IsCurrent()` 失效（显示配置或 HDR 开关变化）或换了显示器时重查。

### 回归

`veyra_screen_capture_tests` 修改前后通过/失败项完全相同。失败的 6 项都是颜色检查：本机桌面开着 HDR，测试的纯红条经 HDR 色调映射后变成 (255,110,115)，用未修改的 main 构建也一样失败。

### 未验证

- 用户的 165 Hz 机器，以及真实游戏和游戏模式（预期从 55 升到 60）。
- 没有这个属性的旧版 Windows：行为保持不变。
- DXGI 兼容方式没有改动。

## 2. 主角对白很轻、OBS 里也一样（日志 68）

### 结论

KUHAIMI G50 交给 Windows 的音频只有双声道（DirectShow 只提供 2ch/1ch PCM），Veyra 收到 FL/FR 后原样输出，没有经过下混。PS5 设为线性 PCM 时，只要采集卡（或它环出的设备）的 EDID 声明支持多声道，PS5 就会发送 5.1/7.1 LPCM。这张卡只取 HDMI 的第 1、2 声道，中置声道（主角对白、过场台词都在这里）在进入电脑之前就丢了，所以 OBS 里也一样。

Veyra 的“强制 PCM”只决定怎样解读采集到的数据，改变不了 PS5 送几个声道，所以没用。

### 修改（`75444b3`）

PS5 设为“位流（杜比/DTS）”时，会把含中置的 5.1 以 IEC 61937 的形式塞进这条双声道“PCM”里传过来。通用 DirectShow 通道原来只做探测、记一条日志，然后把位流当噪声播放。只有 AVerMedia 专用通道会解码。

现在给任意 16-bit 立体声 PCM 引脚加了 `PcmCarrierRouter`（复用已经测过的 `AverMediaAudioCarrier`）：

- 真 PCM 走原路径，时间戳也不变。
- 检测到位流后解码 AC3/E-AC-3/DTS，会话切到带声道掩码的浮点格式，渲染端下混时把中置按 −3 dB 混入左右。
- 位流消失 4 秒后切回 PCM。
- PCM 里偶然出现类似同步字的数据时，0.3 秒内没有第二个包就放行。
- “强制 PCM”模式完全不受影响。

单元测试用真实 AC3 5.1 编码：解码掩码 0x60F，中置声道有信号，没有一个载波字节被当作 PCM 送去播放，4 秒后回到 PCM，误判被放行。另外以下测试都通过：

- `veyra_avermedia_carrier_tests`：39363 项。
- AVerMedia 厂商通道：65+7 项。
- 透传：26+8+8 项。
- IEC 探针测试。
- 采集音频集成测试（静音输出）。

### 给反馈用户的做法

1. **首选（OBS 里同样有效）**：让 PS5 只送双声道。
   - 游戏内音频输出选“立体声/电视扬声器”。
   - PS5 设置→声音→音频输出：确认 HDMI 设备类型为“电视”；有声道数选项的话选 2 声道。PS5 当前菜单没能在线核实，以实机为准。
   - 采集卡环出如果接了功放或回音壁，先拔掉环出试一下：PS5 会按环出设备的能力发送 5.1/7.1。
2. **只适用于 Veyra 的新构建（2.1.1 正式版里没有）**：
   - PS5 的“音频格式（优先）”改为“位流（杜比）”，Veyra 的“Dolby/DTS 位流”保持“自动”，然后重新连接采集。
   - Windows 录音设备“HDMI (KUHAIMI G50)”的级别必须正好是 0 dB：这张卡 100% 对应 +30 dB，会破坏位流。同时关闭音频增强。
   - 前提是采集卡会把位流原样传上来。如果变成无声或噪声，说明卡不支持，改回线性 PCM，按第 1 条处理。

### 未验证

- 没有在 PS5 和采集卡上实测，因为不能占用设备。
- G50 是否原样传送 IEC 61937 只能由用户实测。

## 3. 后续方向（只调研，未动手）

### 效果器候选

现有效果器包括：调色、超分（RTX VSR / DLSS SR K/L/M / FSR / XeSS）、NR、保护、视频 HDR、补帧、抗锯齿、美颜。锐化只存在于 FSR 内部的 RCAS；没有去色带、颗粒、CRT/黑帧插入和对白增强。

| 候选 | 价值 | 成本 / 风险 | 可参考的开源实现（许可证接入前逐项核对） |
| --- | --- | --- | --- |
| 去色带 | 8-bit 采集和压缩串流在转 HDR 或经 NR 提对比后，天空和暗部的色带最明显 | 低；4K 下一次轻量计算 | libplacebo deband（LGPL-2.1+） |
| 独立锐化（RCAS/CAS） | 用户常要的“清晰度”，对 VSR/NR 输出也有效 | 很低；RCAS 代码已在 FSR 后端里 | FidelityFX CAS/RCAS（MIT） |
| CRT 光束模拟 / 黑帧插入 | 60 帧源在 240/320 Hz 屏上的动态清晰度提升很大，正对老游戏采集 | 中；需要按刷新率输出子帧，和补帧、VRR 互斥；165 Hz 这类非整数倍效果打折；要提示闪烁 | Blur Busters CRT Beam Simulator（MIT） |
| 复古扫描线 / CRT 掩膜 | 老游戏用户喜欢 | 中；着色器移植加参数界面 | libretro crt-guest-advanced 等（多为 GPL，需确认“或更高版本”） |
| 对白增强（音频） | 解码出 5.1 后调高中置的下混比例；纯立体声源做中间声道的人声频段增强，直接回应第 2 项这类反馈 | 低；swr 中置混合系数加一个滑条 | FFmpeg swresample |
| 色度重建 | NV12/4:2:0 采集的彩色文字和 UI 边缘更清楚 | 中 | mpv CfL / KrigBilateral 着色器 |
| 胶片颗粒 | 掩盖 NR 的“塑料感”和残余色带 | 低 | 可自写 |

建议先做前两项和对白增强（各 1–2 天，收益确定），再评估 CRT 光束模拟。

### DLSS 5（NR）还能怎么调

沿用 2026-10-26 Lecram v11.9 的研究（`reports/claude-lecram-v119-20261026/RESEARCH.md`）。

- **可做，不改运行库**：
  1. 人物面部保护：先用有人脸的素材验证“自动遮罩 + 肤质”。
  2. 局部明暗从 0–1 放宽到 0–2。
  3. 用 Veyra 自己的着色器做“精调 NR 效果”：按阴影/中间调/高光分别缩放、大范围与细节分开、暗/亮光晕抑制、最大提亮/压暗/变色上限。
  4. 试一下 `DLSSNR.MaskBlendMode` 的取值。
- **性能侧**：已有内部比例、内容去重、60→30、层数。还能做的是按层的 GPU 计时提示，以及在画面静止时跳过 NR。
- **需要另行授权**：RTX 50 改用 NVIDIA 正式签名的 310.9.16 NR 运行库。
- **不做**：改模型权重的“模型实验室”，因为要改动 NVIDIA 运行库。

### DLSS 4.5 光线重构（RR）：不建议接入

- **输入条件不满足**：最新公开 SDK 是 310.9.16（2026-10-16），RR 的 Transformer 模式（Preset F）在 310.9.1 加入。RR 的每帧必需输入是漫反射/镜面反照率、法线、粗糙度、深度、运动矢量（见本机 310.7 头文件 `nvsdk_ngx_helpers_dlssd.h`，新版本没有改变这一点），可选输入还有命中距离、光线方向等。这些都只有游戏引擎内部才有。Veyra 拿到的视频和采集画面只有最终像素。
- **用假数据凑也没意义**：反照率填原图、法线平铺、粗糙度和深度填常数的话，RR 就成了一个在训练分布之外运行、更贵的时间超分，有拖影和过度平滑的风险，也不会比已经接入的 DLSS 4.5 超分（L/M）加 NR 更好。
- **“更干净更细”这个目标**：在最终画面上由 NR 承担，超分由 DLSS 4.5 的 L/M 承担，两者都已在软件里。
