# 真正的双重超分：纠偏与交付（2026-10-28）

## 用户合同

用户明确纠正：普通8K超分继续可用；双重超分必须先完成基础超分，再降低其输出的分辨率，最后执行第二次超分。基础超分下方增加“ 双重超分 ”开关，开启才展开第二次设置。此指令覆盖此前单层“先降→超分→再缩”和最终4K限制；旧报告仅保留诊断与当时验证事实。

施工分支 `codex/dual-sr-20261028`，起点 `67d0294`，存档 `checkpoint/pre-dual-sr-20261028`。同一施工树、同一构建/运行目录；不合并main、不push、不Release。不改真实配置、SDK、模型、DLL、驱动或独立采集分支，Lecram继续暂停。

## 实际链路与界面

`源画面 → 基础RTX视频超分 → 基础AI输出 → 线性光面积降采样 → 第二次RTX视频超分 → 后续效果/输出`。

基础目标和质量保持原字段。新增独立开关、第二次目标、第二次质量；第二次降低尺寸提供720/900/1080/1440p，以及按第一次结果的50–90%手动比例。第二目标提供2K/4K/5K/6K/7K/8K。维持宽高比，不对已经更大的源强行缩小基础SR。第二输入必须小于第一次输出和第二次目标；无有效降低时保留基础处理并显示原因。

列表与节点共用SrStageEditor；基础目标、运动来源、质量下方放双重超分开关，第二次设置随开关展开/收起。关闭后不使用旧先降/再缩字段干预基础超分；不自动将8K改成4K。当前双重功能仅支持RTX视频超分，其他基础后端保留原单次路径，界面明确禁用原因。

ResolutionPlan、固定链计划、实际GPU纹理、状态尺寸、导出共享同一合同。第一AI结果有独立RGBA8/FP16纹理，面积降采样读取其FP16结果；第二次不重新读取原始源。HDR在第一次SR后先做现有代理恢复，再降采样、第二次SR与恢复；不宣称模型原生HDR推理。

## SDK实例与失败修正

首次真实GPU测试遇到NGX `0xBAD00003 / FeatureAlreadyExists`，失败证据保留在 `reports/dual-sr-20261028/gpu-create-key-before.json` 和对应日志。本机SDK即使传入不同创建尺寸仍复用创建键。现在优先创建两个实例；明确收到此返回码时，不取得或释放重复句柄，复用已有Feature，按GPU命令顺序执行两次Evaluate。两个输入/输出纹理及质量参数分别传入，两次都成功才累计两次计数。其他创建/评估错误仍失败，不用普通缩放伪装第二次AI。

本机是“一个SDK Feature、两次实际Evaluate”，不能写成两个独立SDK实例。API合同参考本地nvsdk_ngx.h及[NVIDIA NGX文档](https://docs.nvidia.com/ngx/latest/programming-guide/index.html)，未下载或修改运行时。

## 显存与整机卡死的边界

撤回先前的4K强制修正、恢复时改参数和底层4K拦截。双重图在分配前读取WDDM预算，纹理估算包含第一次输出；额外预留RTX SR 256MiB、NR启用时1GiB、VFG启用时每工作像素128字节，再留可用预算20%余量。不足则拒绝事务，不改请求分辨率。该预留是保守估算，不是SDK显存峰值测量。普通单次路径保持原预算规则，未额外收紧普通8K准入。

原整机卡死转储的事实仍见[旧报告](SR_STAGE_FREEZE_2026-10-28.md)：驱动/系统绘图路径阻塞的候选地址、异常重启，具体根因未证实。本轮未重跑8K最终输出+NR+VFG的原危险组合；预算防护与短测不能证明驱动挂死已根治。
