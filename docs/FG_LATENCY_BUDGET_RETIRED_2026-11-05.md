# 补帧延迟预算：失败方向与终止记录

**状态：已撤销，停止研究。** 2026-11-05 用户明确决定：删除独立功能分支，不继续推进，文档记为失败方向。未经用户重新明确授权，不恢复实现、测试入口或另开分支延续本实验。

## 为什么终止

用户期待“最低档处理不好，自动或＋1／＋2源帧后可以稳定完整处理”的实际案例。本轮没有取得可重复、足以支持该目标的证据：正常负载时最低档已经接近满帧；临界或持续超预算时，增加预算仍有降档和过期，自动档也没有可靠消除这些问题。

最初报告的约182→240次提交/秒混入首次加载等待，核对后已明确撤销，不得再作为功能收益。对照应从实际播放后的稳态区间计算；仅“参数生效、队列扩大、代码可构建、基础回归通过”不能证明功能有实际价值。软件提交计数也不等于屏幕实际显示帧率。

实现目标与用户需求存在偏差：本实验给原实时调度增加有限等待／文件预读，赶不上期限仍会降档；它没有实现“完整处理优先，宁可等待或重新缓冲也不减少补帧”。小缓存可能吸收短时波动，但不能增加持续处理吞吐。这里否定的是本项目这条实现和交付方向，不能扩大解释为所有缓冲机制都无效。

新增输出池、显存准入、截止时间、音画重置与持久化逻辑增加了维护和回归风险，而收益未充分证明。按用户决定撤销，不再增加预算档位、调整参数寻找宣传案例或继续扩展。
