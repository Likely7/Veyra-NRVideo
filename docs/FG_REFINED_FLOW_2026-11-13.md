## 改了什么

### 原来

- XeSS 走呈现器补帧，运动来源选"光流"时，用的是精修过的光流（边缘神盾）：
  - `FlowRefine`：按像素在相邻 3×3 块的矢量里挑与上一帧最匹配的一个；NVOF 时附带前后向一致性检查，AMD 光流用 `FlowClaim`。
  - `FlowFill`：找不到对应的像素（被遮挡后露出的背景），借相邻可信像素的矢量。
- DLSS / FSR / ANR 在图里补帧，用的是按块复制的 `baseFlow_`；出界或代价高的矢量直接清零。

### 现在

- **启用范围**：`flowRefine_` 改为"XeSS 呈现器补帧"或"图内补帧"都启用，但只限用光流运动的后端；VFG 自带运动估计，不涉及。
- **运动来源**：图内补帧的运动输入（`EnhanceGraph.cpp` 中 DLSS、ANR、FSR 共用的那一处）在精修开启时改用 `fgBaseFlow_`。它与 `baseFlow_` 单位相同（当前→上一帧，工作分辨率像素），ANR 与 DLSS 各自的缩放约定不变。
- **设置归一化**：`EnhancementSettings::activeVideoSettings` 对所有用光流运动的补帧保留 `fgMotionRefine`。XeSS 仍只在运动来源为"光流"时生效；VFG 以及零运动时回到默认值。
- **图的原地套用检查**：图内补帧在"边缘神盾"变化时也要求重建，因为精修自带纹理、计算步骤，并会改变 NVOF 的方向配置。
- **日志**：新增 `graph FG motion: refined NVOF (FlowRefine+FlowFill, forward-backward)` 一类记录；XeSS 仍写 `present-sink FG motion: …`。
- **界面**：
  - 列表页"边缘神盾"的提示改为"DLSS、FSR、ANR 补帧，及运动来源选'光流'的 XeSS 生效"；节点页去掉"XeSS"字样。
  - 四种语言的词库原位替换两条，不重排。
- **开关与默认**：开关仍是"边缘神盾"（`fgMotionRefine`），默认开启，并与原来一样保存在界面偏好里。
- **测试**：
  - `RepairFgTests` 新增 `-hud` 测量模式：在高速平移的细节纹理上叠一块静止条纹 UI。每张生成帧输出 UI 区域、左右各 48 像素边缘带、内部的平均绝对误差，基准是解析出的中间帧，边缘处移入的内容也有精确真值。
  - 新增提供方参数 `fsr`。
  - 不加新的通过门槛。

## 代价

- **每对补帧的额外开销**：用 NVIDIA 光流时，精修会开启前后向一致性检查，NVOF 多跑一次反向光流，再加上 Refine、Fill、Adapt 三个计算步骤。推算每对补帧多约 1–1.5 ms GPU，计入 `gpuFlowP95Ms`。本轮只有合成测试，没有实测这部分耗时。
- **显存**：约为 光流尺寸 × 13 字节 + 工作尺寸 × 4 字节。1080p 光流、4K 输出时约 60 MB，已计入显存预算估算。

- **纯平移**：ANR 精修光流的误差（边缘 0.743、内部 0.322）几乎等于精确运动（0.736 / 0.322）。

### 结论与边界

- **边缘闪烁**：ANR、FSR 的画面边缘误差下降 84–90%。原来出界矢量被清零，边缘一带按静止处理；精修保留了真实运动。
- **DLSS 基本不变**：DLSS 补帧内部还有自己的光流，我们送入的矢量对它影响小。它在这个测试里 UI 也处理得好。
- **静止 UI 的糊不能靠精修解决**：被高速运动的纹理包围时，UI 内部和周围块的矢量都被带偏，3×3 候选里没有正确的零矢量，误差反而略增约 2%。需要另做 UI 自动保护（直接比较前后帧，判定静止的像素运动置零并合回）。
- **未覆盖**：
  - AMD FidelityFX 光流（走 `FlowClaim`）没有跑 `-hud` 测量。
  - 实机效果和实际 GPU 耗时待用户用手动入口对比。
