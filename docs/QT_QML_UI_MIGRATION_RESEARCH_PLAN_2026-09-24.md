# Qt Quick / QML 前端迁移调研与初步方案

日期：2026-09-24
状态：只读调研与方案；没有修改产品代码、安装 Qt、构建或运行新程序。

## 结论

Qt Quick/QML 适合承担高观赏性的播放器界面：动画、排版、状态切换和统一控件样式都比继续堆 Win32 控件更直接。但它不是给现有程序换一层皮。Veyra 的 D3D12 播放画面绑定在一个原生 Win32 `HWND` 上，Qt Quick 的 QML 场景则由 Qt 的窗口/场景图系统绘制。两者要在同一个窗口内叠放，首先要解决原生窗口层级；窗口父子关系、尺寸变化和全屏过程也必须继续满足现有 DXGI 生命周期要求。

普通窗口不需要让 QML 控件压在视频上：当前日常模式的播放栏就在视频下方，专业模式的参数区在视频右侧。全屏是例外，视频铺满窗口，底部控制栏叠在画面上并自动隐藏。建议 QML 先接管普通窗口中视频以外的界面，同时保留现有原生全屏控制栏和字幕覆盖层；先验证 Qt 外壳能否保留这些 HWND 的层级和生命周期。只有后续要把全屏控制栏也改成 QML 时，才单独验证 QML 覆盖。

原型保留 `EngineController`、`VideoPresenter`、`PresentSink`、解码、音频和增强图。若现有原生全屏控制栏无法在 Qt 外壳下可靠工作，或窗口集成造成可重复的呈现退化，应停止外壳迁移并评估局部 QML 面板或现有 Win32/Direct2D 路线。现在不能承诺完全不影响延迟或稳定性。

UI 组件闪烁与视频画面欠速闪烁是两类问题。QML 可能改善 UI 绘制和交互的一致性，但不会自动修复播放器调度、补帧或显示同步问题；额外的 QML 绘制也可能增加 GPU 负载。

## 现有结构

- 项目是 Windows x64、C++20、Win32、D3D12；`CMakeLists.txt` 中 `veyra` 是 Win32 可执行目标，目前没有 Qt `find_package`、QML 模块或 Qt 链接配置。
- `apps/veyra/ui/AppShell.cpp` 创建主窗口和多个 Win32 子控件。视频控件 `video` 也是主窗口的子 `HWND`；打开媒体时调用 `engine.open(video, ...)`，不是将视频帧交给 UI 控件绘制。
- `EngineController::open(HWND, ...)` 将视频窗口句柄传入播放侧。当前命令接口和 `PlayerSnapshot` 可作为新 UI 适配层的基础，但 QML 不应直接持有或调用播放器内部对象。
- `PresentSink` 通过 `IDXGIFactory::CreateSwapChainForHwnd` 将 D3D12 队列的交换链绑定到该视频 `HWND`。窗口尺寸改变时，呈现侧会等待队列空闲再调用 `ResizeBuffers`。现有代码还明确记录：swapchain 释放前，目标 `HWND` 必须仍然存在。
- `docs/UI_DUAL_MODE_EXECUTION_PLAN_2026-09-08.md` 之前的已确认 UI 方向是保留 Win32 窗口和视频宿主，并用 Direct2D/DirectWrite 改进控件外观。本调研是对 Qt Quick 替代路线的评估，不自动改写该方案或授权开始迁移。
- 问题台账 `U1` 记录 UI 快速滚动、拖动和高 DPI 覆盖尚有验收边界；`F1` 的欠速/补帧闪烁另列为播放器问题。改 UI 框架不能把 F1 视为已修复。

## 窗口集成路线

| 路线 | 优点 | 主要限制 | 初步判断 |
| --- | --- | --- | --- |
| Qt Quick 作为主窗口，原生视频 `HWND` 作为子窗口 | QML 管理视频以外的主界面；原视频窗口和 Present 链路可保留 | 必须验证 Qt 主窗口下视频、现有原生全屏栏和字幕窗口的父子关系、Z 顺序与生命周期 | 推荐作为首个原型；普通窗口不要求 QML 覆盖视频，全屏先保留原生控制栏 |
| Qt Widgets 主窗口中放 `QQuickWidget`，视频 `HWND` 独立保留 | 便于逐页迁移，QML 内容可作为普通 widget 区域参与布局 | `QQuickWidget` 先渲染到离屏纹理再合成，增加 GPU 工作；它的透明区域不能按普通透明 widget 那样显示下面内容；与原生视频窗口的 Z 顺序仍须在 Windows 上实测 | 可用于设置页、侧栏等非覆盖区域；不能先假设能做视频上方浮层 |
| 将原生视频窗口包装成 Qt 外部 `QWindow`/`createWindowContainer` | Qt 布局系统可管理外部窗口的位置和尺寸 | Qt 官方文档说明外部窗口句柄仍由应用负责生命周期；window container 有原生窗口叠放限制 | 能管理几何，不代表能让 QML 无缝覆盖视频 |
| 单独创建透明 QML 浮层窗口盖住视频 | 可将全屏控制栏也迁移到 QML | 可能改变 DWM 合成、独立翻转资格、HDR/OBS 捕获和全屏表现；浮层与视频也可能不同步 | 非首阶段要求；仅在需要 QML 全屏栏时另做原型 |
| 把视频画面改成 QML 场景的一部分 | QML 布局和叠放最自然 | 会改动 D3D12/DXGI 呈现和纹理互操作路径，超出“保留现有播放画面链路”的安全范围 | 本轮不建议作为迁移方案 |

Qt 官方文档给出的相关约束：

- [QQuickWidget 性能说明](https://doc.qt.io/qt-6/qquickwidget.html#performance-considerations)：场景会先绘制到离屏颜色缓冲，再绘制纹理四边形，增加 GPU 负担；文档也说明透明 `QQuickWidget` 不会按预期显示其下方普通 widget。
- [QWidget::createWindowContainer](https://doc.qt.io/qt-6/qwidget.html#createWindowContainer)：原生 `QWindow` 容器受窗口层级和叠放限制。
- [QWindow::fromWinId](https://doc.qt.io/qt-6/qwindow.html#fromWinId)：外部原生窗口的句柄不转移给 Qt 所有，应用必须保证其生命周期。
- [QQuickRenderControl](https://doc.qt.io/qt-6/qquickrendercontrol.html)：可以由应用控制 Quick 场景离屏渲染，但这本身不会解决与现有 D3D12 交换链之间的同步、共享资源和合成问题，不适合作为首个试验捷径。

## 对播放链路的影响判断

如果 Qt 只负责控件和窗口管理，并且原有视频 `HWND`、`EngineController::open(HWND, ...)`、D3D12 队列、`CreateSwapChainForHwnd` 与 Present 调用均保持不变，那么解码、增强、音频时钟及每帧视频呈现代码可以不改。这使“保留引擎”在架构上可行，但不等于窗口迁移没有运行影响。

| 风险 | 影响机制 | 方案约束 / 原型检查 |
| --- | --- | --- |
| `HWND` 重建或提前销毁 | swapchain 绑定目标失效，已有记录证明会导致呈现释放问题 | 打开播放后保持视频 `HWND` 身份稳定；先停止并释放播放侧资源，再销毁窗口；模式切换不重开源、不换句柄 |
| 视频区域连续变化 | resize 需要队列 drain 和 `ResizeBuffers`，会占用播放时间 | QML 动画不逐帧调整视频宿主尺寸；布局变化合并为一次最终尺寸提交，沿用并核验现有 resize 节流 |
| 全屏控制栏与字幕覆盖视频 | 普通窗口中 UI 可避开视频；全屏栏和字幕需要原生覆盖窗口位于视频 HWND 上方，Qt 外壳切换可能改变父子关系或 Z 顺序 | 首阶段沿用现有 Win32 overlay HWND；测试全屏显隐、鼠标命中、字幕、失焦恢复；QML 覆盖作为后续独立选项 |
| 独立 Qt 绘制负载 | Quick 场景可增加 GPU/CPU 绘制与合成工作，可能与 D3D12 竞争 | 不在 QML 传递帧像素或运行增强；少量、按需更新状态；对比同一媒体的提交间隔、GPU 时间和掉帧 |
| Qt 事件循环与 Win32 消息 | `QApplication::exec()` 将成为 UI 主循环，现有 Win32 窗口过程和定时器需迁移/桥接 | Qt UI 线程只处理 UI；播放、解码和文件工作仍留在既有 worker；禁止 UI 线程等待 GPU、解码或导出 |
| HDR、全屏、DPI、OBS | 新宿主可能改变显示器识别、窗口合成或采集到的层级 | 单独验证 HDR 输出状态、跨 DPI/显示器、全屏进出、锁屏、OBS 窗口捕获和截图 |
| 发布体积与维护 | Qt Quick 运行库、平台插件、QML 模块和部署工具加入包；Qt 组件有各自许可要求 | 定版本、审计实际用到的模块许可证和部署文件，再测干净机器启动；不把 SDK、插件从开发机无清单复制进正式包 |

## 初步实施阶段

### 0. 保护当前基线

以当前已验收版本和 UI 测试作为对照，保存实际使用的媒体、启动参数、日志、程序哈希及窗口行为证据。至少覆盖普通播放、暂停/seek、日常/专业模式、全屏、HDR 状态、缩放/DPI 和退出。所有比较用同一台机器、同一媒体和同一显示设置；UI 刷新表现与视频提交指标分开记录。

### 1. 隔离窗口原型

在独立分支和 `qt_ui_probe` 目标中接入 Qt Quick，不重构 `veyra_engine`。原型必须使用真实 `EngineController` 和真实 `PresentSink`，保留同一个原生视频 `HWND`，不能用静态图片或 QML 视频控件代替。普通窗口中将 QML 控件布置在视频矩形以外；全屏沿用现有原生控制栏和字幕覆盖层。集中回答：

1. 视频 `HWND` 从打开到停止是否保持同一数值，且生命周期覆盖 swapchain。
2. Qt 外壳下现有 Win32 全屏控制栏是否仍在视频上方，鼠标命中、自动隐藏和字幕覆盖是否正常。
3. resize、DPI、跨屏、HDR 和 OBS 窗口捕获是否与基线一致。
4. 播放日志中是否出现额外源重开、seek、图重置、Feature 重建或非用户请求的 `ResizeBuffers`。
5. 同条件下源帧提交间隔、GPU/CPU 时间和丢帧是否出现可重复退化。

若需要把现有全屏控制栏迁移为 QML，再增加一组全屏覆盖对照；这不是普通窗口 QML 接入的前置条件。

窗口和模式切换沿用既有 UI 方案中的临时门槛：UI 命令 P95 不高于 16 ms、单次不高于 50 ms；稳定 60 源 fps 下由纯 UI 布局操作引起的额外连续提交间隔不高于 100 ms。比较前要排除媒体场景切换、用户 seek、增强设置改变和导出竞争；这些数字是原方案的目标，不是本次已测结果。

### 2. 建立 UI 适配层

仅在原型通过后，加入窄接口的 `PlayerUiFacade`：将 `EngineController` 命令作为 UI action，将所需 `PlayerSnapshot` 字段变成 QML 属性/模型。QML 不接触 D3D12 资源、帧缓冲、媒体解码对象或音频时钟，也不直接持有 `EngineController`。更新按状态变化合并，不在每次动画帧复制完整快照或诊断列表；播放控制命令保持异步，不让 UI 线程等待引擎操作。

### 3. 分区迁移与功能对等

先迁移普通窗口中视频矩形以外的主框架、侧栏、设置页、状态展示和播放控制。全屏继续使用现有原生控制栏叠在视频上，字幕覆盖也先保留现有实现；后续可单独把全屏栏换成 QML 并比较结果。若 QML 全屏覆盖不可靠，保留原生栏不构成普通窗口迁移失败，也不能为了覆盖而改 Present 路径。采集、PS5、字幕、比较、诊断、导出和偏好设置逐项迁移并保持原命令语义，不能在一次 UI 改写里重写其业务逻辑。

### 4. 回归与交付门槛

至少通过：播放/暂停/停止/seek、源切换、截图、采集连接、PS5、字幕、比较/缩放、设置应用失败回滚、HDR、全屏/多 DPI、导出生命周期、窗口关闭期间的引擎释放；视觉检查覆盖小窗口、普通播放、设置页、全屏、弹窗和深浅状态变化。自动检查确认 UI 操作不增加源打开、seek、设置 revision 或图重置。报告 UI 观感结果和播放性能结果，不用 UI 测试通过代替实卡、HDR 显示器或 OBS 验收。

## 停止条件

- Qt 外壳无法在不改变 `CreateSwapChainForHwnd` 和 D3D12 present 路径的情况下承载现有视频 HWND 及原生全屏控制栏：停止外壳迁移，先单独评估窗口架构影响。
- 把全屏控制栏改成 QML 需要更改 Present 路径或让视频帧进入 CPU/QML 图像对象：取消 QML 覆盖选项，保留现有原生栏；这不阻止视频以外 UI 继续评估 Qt。
- 同条件实测出现可重复的 Present 间隔、GPU/CPU 开销、HDR、全屏或 OBS 回归，且无法在不改播放链路的情况下消除：停止整壳迁移。
- 普通窗口 QML 区域与视频没有可靠的 HWND 层级/输入路由：将 QML 限定为独立设置页或侧栏，并保留 Win32 播放外壳，重新评估是否值得迁移。
- 正式打包前必须固定 Qt 版本、部署工具、实际运行模块及许可证清单；当前未完成这些审计。
