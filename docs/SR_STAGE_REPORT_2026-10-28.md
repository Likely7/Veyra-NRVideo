## 1. 做了什么

超分卡片（列表模式）和超分节点（节点模式）共用新组件`SrStageEditor.qml`：**先降到 → 超分到 → 再缩到**，另有“实际尺寸”一行显示引擎正在使用的尺寸。

| 设置 | 选项 | 存储 |
|---|---|---|
| 先降到 | 关闭 / 720p / 900p / 1080p / 1440p / 手动 50–90% | `SrPrescale`，手动=100+百分比 |
| 超分到 | 原“目标尺寸”，2K–8K 不变 | `SrTarget` |
| 再缩到 | 不缩 / 片源尺寸 / 2K / 4K / 5K / 6K / 7K | `SrOutput` |

- 尺寸：`srStageExtents`（`ResolutionPlan.h`）统一给出“先降后 / SR 结果 / 步骤输出”。先降后已无法再放大、或再缩框不小于 SR 结果时，该步“未生效”并在界面写明原因，不报错。`ResolutionPlan`新增`srInput/srOutput`；链路编译的 SR 步骤`processing`=SR 结果、`output`=再缩后尺寸。
- 只在 RTX 视频超分（质量 1–4、NVIDIA）运行：`runningSrPrescale/Output`对其他后端/显卡给出关闭值；`activeVideoSettings`同样归一化，所以 DLSS/FSR 下改这两项不重建图；界面两行禁用并写“目前仅 RTX 视频超分支持”，桥接也拒绝写入。
- GPU（`EnhanceGraph.cpp` VSR 分支）：先降复用`NrDownsample.dxil`精确面积缩小（线性光）到`srPrescaled_`；`videoSrInput_/videoSrOutput_`按先降尺寸/SR 结果尺寸分配；再缩用新`SrResolve.hlsl`，逐 SR 像素先解码（SDR）或 HDR 还原，再按面积权重平均写入工作纹理，不分配 8K FP16 中间纹理。HDR 还原所用底图与代理输入同为先降尺寸。全部在原命令列表内，无回读、无 CPU 等待；`GpuStage::Sr`计时包含先降和再缩。
- 采集卡原尺寸跳过、压缩视频原尺寸修复等原规则在“先降关闭/不缩”时不变；开启先降后，采集源与静态图片也执行（用户显式选择）。
- 重建：`requiresGraphRebuild`与引擎尺寸比较都加入新项；日志`[video-sr] selected ... three-step prescale=WxH evaluate=WxH`。
- 存储：PresetStore v33、预设库 v16、模式会话 v11，只有用到新项才写新版本；库/会话写入新的`.sr-stage`旁路文件，旧文件保留供 2.1.1 回退。
- i18n：15 条新文案补齐繁中/英/日，`extract.py --check`缺失 0。

与方案的差异：`HdrVideoSrRestore.hlsl`未改动，`SrResolve.hlsl`直接用`HdrColor.hlsli`的`HdrRestore`并自带同样的双线性采样，避免改动现有 HDR 路径；HDR 正确性改由下文第 3 节的比对证明。

## 4. 图片 A/B（RTX 视频超分质量 4，RTX 5070）

素材：用户附件实际是 2000×1125、69KB 的 webp（聊天传输压缩过，不是原生 4K 原图）；有参照的对比改用项目以前用过的本地原生 4K 自然视频`GTAVI_An_Extended_Look_4K_Native.mp4`，抽取 t=780 秒（城市+HUD 小地图）和 t=95 秒（人物/金属/纹理）两帧无损 PNG 作参照。退化：糊的 4K = 面积缩到 1080p→JPEG q70→双三次放回 4K；原生 2K = Lanczos 缩到 2560×1440。PSNR/SSIM 按亮度对参照计算；“锐度”是梯度均值（参照 t780 为 0.00736、t95 为 0.00601），超过参照多半是过锐/光晕。

| 场景 / 方式 | t780 PSNR / SSIM / 锐度 | t95 PSNR / SSIM / 锐度 | SR 耗时 |
|---|---|---|---|
| 糊 4K：不超分 | 41.65 / 0.9780 / 0.0062 | 43.85 / 0.9744 / 0.0031 | – |
| 糊 4K：现有单步（4K 原尺寸修复） | 40.91 / 0.9706 / 0.0090 | 42.77 / 0.9664 / 0.0063 | 23.1 ms |
| 糊 4K：先降 1440p→4K | 40.49 / 0.9668 / 0.0093 | 42.24 / 0.9626 / 0.0066 | 10.5 ms |
| 糊 4K：先降 1080p→4K | 40.96 / 0.9659 / 0.0094 | 42.56 / 0.9638 / 0.0069 | 6.0 ms |
| 糊 4K：先降 1080p→8K→4K | 40.98 / 0.9695 / 0.0083 | 42.53 / 0.9646 / 0.0057 | 7.2 ms |
| 原生 2K：双三次放大 | 48.63 / 0.9957 / 0.0068 | 51.86 / 0.9941 / 0.0048 | – |
| 原生 2K：现有单步 2K→4K | 44.76 / 0.9805 / 0.0095 | 45.74 / 0.9781 / 0.0071 | 10.5 ms |
| 原生 2K：2K→8K→4K | **45.40 / 0.9835** / 0.0085 | **46.52 / 0.9812** / 0.0062 | 11.5 ms |
| 原生 2K：先降 1080p→4K | 42.57 / 0.9757 / 0.0093 | 44.54 / 0.9731 / 0.0068 | 6.0 ms |

结论（两帧，结果可复现）：

- **原生 2K 想更清楚：2K→8K→4K 在两帧上 PSNR、SSIM 都高于现有单步，锐度更接近原图**，1:1 观感也更自然；单步明显偏过锐。
- **糊的 4K：三段式在客观分上与现有单步基本持平**（1080p→8K→4K 的 PSNR 略高、SSIM 略低），主要收益是开销降到 1/3–1/4（23 ms→6–7 ms）。观感差别需要用户自己看裁切图判断。
- 所有 AI 超分的 PSNR 都低于双三次/不超分，这是重建细节类方法的常态，数值不当最终结论。
- **已知限制得到量化**：把原图清晰的小地图贴回糊画面（模拟 PS5“画面糊、HUD 原生 4K”），HUD 区域 PSNR 单步 44.19 dB，先降后 35.0–36.6 dB；文字仍可读但边缘改变。这正是第二阶段“细节保留混合”要解决的。
- 用户附件（2000×1125 放大成糊 4K，无参照）：先降 1080p→4K 6.7 ms，现有单步 26.4 ms；压缩块明显减少、边缘更干净，但这张图压缩太重，看不出真实细节差异。
