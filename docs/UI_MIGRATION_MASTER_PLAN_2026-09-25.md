## 0. 用户本轮决定（2026-09-25）

1. NR 叠层和自由排序照搬 Magpie 的做法，不再单独做“能不能行”的可行性论证。
2. 节点模式要做到“想怎么调就怎么调”。
3. **不保留旧界面**，全部换成新界面。
4. **设计稿里有、当前版本没有的功能，全部要做**，包括：

   - 音频输出设备与下混
   - 导出码率控制三选一

   - 调色按组还原
   - 设置页
   - 预设管理
   - 导出队列与剪辑范围
5. **导出分辨率可以自定义。**
6. 取消单独的 NR 预设，所有预设统一成一种。保存时可以勾选要包含哪些部分，和设计稿一致。
7. **不做内测阶段。**
8. 在一个分支上完成，不拆多个分支。

## 1. Magpie 源码核实结果（`SAOG0721/Magpie` experimental，提交 `3841698`）

| 问题 | Magpie 的实际做法 | 对 Veyra 的意义 |
|---|---|---|
| NR 怎么加载 | 整个进程共享一个“片段会话”：加载 `nvngx_dlssnr.dll`、`Init_Ext`、给片段的 `GetModuleFileNameW` 打 IAT 钩子，钩子由进程全局标志保护（`DLSSNRFilter.cpp` 约 L697-944、L1380-1455） | 和 Veyra 的 `DlssNrRuntimeAdapter` 是同一套机制。“不能每层各开一个 adapter”的限制两边都有 |
| 多层 NR 怎么实现 | **每层各自一个 NGX 句柄**：每个 `DLSSNRFilter` 有自己的 `CreateFeature`、参数块、命令队列和历史；多个 NR 共用那一个片段会话（`DLSSNRMultiPass.h` L37-111，`DLSSNR-MULTIPASS.md` L31-51） | **叠层可行，照这个结构移植**：一个 adapter，多个句柄，每层独立纹理、参数和历史 |
| 每层参数 | 风格、强度、局部明暗、局部结构、肤质、自动遮罩、UI 修正这 7 项按层独立；分辨率、残差、光流由各层共享 | Veyra 要求每层所有参数都独立，比 Magpie 多一步，但机制相同 |
| 上游改参数 | 下游 NR 的 `inputRevision` 加 1，下游历史重置 | 照搬：任意一层变化，都重置它后面各层的历史 |
| 光流 | 每个抓帧只算一次，按各层需要的尺寸分发；中间结果不重新估算光流 | 照搬：光流按源帧计算一次，由所有需要它的节点共享 |
| 顺序限制 | 除了“最多一个补帧”，没有其他顺序校验。DLSSNR 自己要求输入输出同尺寸，SDR 用 RGBA8，HDR 走实验路线 | 节点模式放开顺序，每个节点自己声明尺寸和色彩域要求，执行器负责转换 |
| **补帧放在 NR 前面** | **补帧节点只是一个标记，自身什么都不处理，直接透传。真正的补帧始终在整条链的最终输出上执行一次**（`Renderer.cpp` L1892-1928）。补帧节点后面的效果只处理真实帧，**不会处理生成帧** | Magpie 也**没有**“先生成中间帧、再对中间帧做 NR”。见下方 §1.1 |
| D3D11 与 D3D12 | Magpie 渲染器是 D3D11，通过共享纹理和共享 fence 调用 D3D12 的 NGX | Veyra 本身就是 D3D12，这部分不需要 |
| 许可 | 仓库整体 GPLv3，文件内没有单独的许可头；NGX 头文件和 DLL 不在仓库里 | 可以移植 Magpie 自己的代码，逐项登记来源；NGX SDK 文件不能复制 |

### 1.1 “补帧放在 NR 前面”怎么做

有两种可选含义：

- **A. 照搬 Magpie（推荐，本方案默认）**：补帧节点可以放在链路的任何位置，但实际仍在输出端执行。节点上标注“在输出端执行”，并用虚线把它和真正的执行位置连起来，界面不做误导。这样安全，性能也可预期。
- **B. 真正对生成帧做后处理**：生成帧出来以后，再让 NR 或调色处理每一个呈现帧。这需要：
  - 每个呈现帧都跑一遍后面的效果：2X 成本翻倍，4X 翻四倍；
  - NR 的时域历史要能分辨真实帧和生成帧；
  - XeSS 和 FSR 的补帧在呈现器内部完成，拿不到生成帧，这种顺序只能用于 DLSS 补帧。

  Magpie 没有这种做法，没有现成代码可以照搬。可以作为后续的独立实验项，本方案不包含。

## 2. 总体顺序

一个分支，四段依次推进。每段结束打存档点，并做一次完整回归：

```text
S0 基线 → S1 引擎地基（画面不变）→ S2 引擎新能力（NR 叠层 / 独立调色 / 可排序执行器 / 导出补齐 / 小项）
        → S3 Qt 窗口探针 → S4 QML 新界面（全功能）→ S5 删除旧界面、打包 → 用户验收 → 合并 main
```

**为什么先改引擎、再换界面：**
- 不保留旧界面，也不做内测，所以新界面上线时就必须是完整功能。
- 如果先迁界面，再往里补引擎能力，新界面就要经历多次“半成品”状态，而且没有旧界面可以对照。
- 先在旧界面还在的时候把引擎改好，每一步都能用现有测试和旧界面做对比，确认画面和性能没有退化。
- 引擎稳定后再做界面，界面阶段出的问题就一定是界面问题。

**S3 Qt 探针可以提前到 S1 期间做。** 它不改引擎，只有一个独立的探针目标，不影响主线。

## 3. 分支与安全规则

- **分支**：只开一个，`codex/ui-qml-migration-20260925`，从 main 当前提交开出。
- **存档点**：每段开工前打标签 `checkpoint/ui-mig-<段>-pre`，结束时打 `checkpoint/ui-mig-<段>-done`。任何一步失败，都可以回到上一个存档点。
- **提交粒度**：每个编号步骤单独提交，提交信息写明步骤编号，方便定位和回退。
- **画面不变的步骤必须逐像素对比**：用 S0 固定的抓帧用例比对哈希，出现差异就停下查原因。
- **新引擎能力在 S2 期间带开关**：默认关闭，关闭时走原路径。S4 新界面接入后，由界面上的实际设置决定是否启用；开关本身保留为诊断用途。
- **设置文件只增不毁**：新格式写新文件；旧文件只读迁移，失败时保留原文件并提示。
- **规则不变的部分**：
  - 运行组件身份、源码与二进制隔离、许可证规则照旧；
  - Qt 装到 `E:\项目\Veyra\deps\qt\<版本>`；
  - 构建产物放在 `E:\项目\Veyra\build\ui-qml-migration-20260925`；
  - 测试和日志放在 `E:\项目\Veyra\tests|logs\ui-qml-migration-20260925`。
- **合并 main、推送、发布**：分支完成后由用户验收，合并前再次确认。push 和 Release 需要用户在当时的对话里另行授权。
- **如实报告**：
  - 本机 RTX 5070 的结果不外推到其他显卡；
  - 提交帧率不冒充显示帧率；
  - 没做的测试写“未执行”；
  - 节点模式新增的效果组合，画质一律标“未验证”。

### S2 引擎新能力

每一项都是：实现 → 抓帧 / 性能 / 稳定性验证 → 打开开关。

- **S2.1 NR 叠层（移植 Magpie 结构）**
  - 一个 `DlssNrRuntimeAdapter` 会话创建多个 Feature 18 句柄；三种运行时（原版、社区版、RTX 30 兼容）都走同一个会话。
  - 新建 `NrInstance`，每层独立拥有：
    - 句柄和参数块；
    - proxy / neural / final / residual 纹理；
    - `NrTemporalPass`；
    - `inputRevision`。
  - 上一层输出作为下一层输入。上游变化时，重置下游各层历史。
  - 所有 12 个参数和“时域防闪烁”按层独立。
  - 保护区域从残差 pass 里拆成独立的一步，放在最后一层 NR 之后。这样修复了“不开 NR 时保护区域无效”的问题。
  - 光流每个源帧只算一次，各层共享。
  - 来源登记到 `THIRD_PARTY_NOTICES.md`：Magpie `3841698`，`DLSSNRFilter.cpp` / `DLSSNRMultiPass.h`，GPLv3，写明改动内容。
  - 验证：
    - 1 层时抓帧哈希与 S0 一致；
    - 2、3、4 层在三种运行时下都能连续播放 10 分钟；
    - seek、换源、暂停恢复、窗口 resize、设备丢失后，每层都正确重置；
    - 记录每层的显存和 GPU 耗时；
    - 1–4 层画质对比截图交给用户看。
  - 停止条件：本机上某种运行时的多句柄出现崩溃或错误输出时，停下报告。可以把该运行时限制为单层，不影响其他运行时。

- **S2.2 独立调色 pass（多实例）**
  - 新增 RGBA16F 调色 compute pass，每个实例有自己的调色表和 LUT。
  - 链路里只有一个调色、并且在最前面时，继续走原来融合在导入着色器里的路径，性能不变。
  - 新增“按组还原”的引擎支持：按调色的 7 组分别恢复默认值。
  - 验证：融合路径和独立 pass 放在同一位置时，输出差异在记录的误差内；6 个实例同时开启时正常。

- **S2.3 可排序执行器**
  - 把 `EnhanceGraph::process()` 改成按效果链执行的 pass 列表。每个 pass 声明输入输出尺寸和色彩域，执行器负责：
    - 准备中间纹理（RGBA16F 双缓冲）；
    - 在需要时插入尺寸或色彩域转换，例如 HDR 之后接 NR 时，先做 HDR→SDR 代理编码，再用现有的 HDR 保留合成回来；
    - 按“源帧光流只算一次”分发给各节点。
  - 分两步做：
    1. **只跑现有两种顺序**（默认顺序、NR→SR 低延迟）。抓帧哈希必须与 S0 一致，之后删除约 20 处 `nrBeforeSr` 分支。
    2. **放开任意顺序**，唯一硬性规则是补帧在输出端执行（§1.1 方案 A）。
  - 验证：
    - 固定顺序时哈希一致；
    - 随机生成 200 条合法链做冒烟测试：能建图、能出帧、无 D3D12 调试层错误、能正确 reset；
    - 常用的 20 条链记录性能；
    - 新增组合的画质一律标“未验证”。
  - 停止条件：固定顺序的哈希对不上时，不进入第 2 步。

- **S2.4 节点链运行**
  - 用 S2.3 的执行器运行节点模式的链。
  - 画布上没有接入链路的节点不创建资源。
  - 列表 / 节点两套配置分别保存，切换时重建。
  - 验证：两种模式来回切换 50 次，没有泄漏（显存和句柄数回到原值）；切回列表后，设置和切换前一致。

- **S2.5 导出补齐**
  - 自定义输出分辨率：在链路之后加一步最终缩放，宽高可以任意设置，受编码器上限约束。选择“跟随预设”时，使用超分的目标尺寸。
  - 剪辑范围：入点和出点；seek 后在第一个完整帧开始，音频同步截取。
  - 多文件队列：按顺序依次执行，前一个完成后自动开始下一个。
  - 码率控制三选一：CBR、VBR、恒定质量，NVENC 和 Media Foundation 都要支持；码率可以任意填写，上限按编码器能力。
  - 剩余时间估算。
  - 按预设导出：可以选列表或节点预设，导出时冻结该预设。
  - 验证：每种组合导出短片，检查分辨率、时长、音画同步、码率偏差和中途取消。

## 5. 风险与应对

| 风险 | 在哪一步暴露 | 应对 |
|---|---|---|
| 某种 NR 运行时不支持多个句柄 | S2.1 | 只把该运行时限制为单层，界面标注原因；其他运行时不受影响 |
| NR 叠层显存或耗时过高，实时播放跑不动 | S2.1 | 实时层数上限按实测决定，导出可以更多；界面显示预计耗时 |
| 任意顺序导致色彩或尺寸出错 | S2.3 | 执行器统一做转换并有校验；200 条随机链冒烟测试；画质标“未验证” |
| Qt 浮层盖不住视频，或造成呈现退化 | S3 | 停下报告，改用 Win32 外壳 + 局部 QML 的备选方案 |
| 不保留旧界面、没有内测，上线后发现漏功能 | S4.10 | 功能对等清单全部勾完才进入 S5；S5 前再做一次完整回归 |
| 单分支周期长，main 上同时有其他修复 | 全程 | 每段结束把 main 的新提交合并进分支并回归，不等到最后一起合 |
| Qt 版本或模块许可问题 | S3.1 / S5.2 | 固定版本，逐个模块审计，只用 LGPL 可动态链接的模块 |

## 6. 用户最终决定（2026-09-25，开工前）

- **补帧锁定在最后**：列表和节点模式都一样。节点模式把补帧拖到别处时拒绝，并提示“补帧只能放在最后”。§1.1 的方案 A 和方案 B 都不做。
- **HDR 位置**：RTX Video HDR 之后只能接补帧（NR 等放在 HDR 之后无效）。
- **显示帧率**：不另做。RTSS / 微星小飞机统计的是程序每秒 Present 的次数，和我们的“提交帧率”同一口径，所以界面继续只显示提交帧率。设计稿里的“显示 fps”改回“提交 fps”。§1.7、S1.7、S2.6 中相关内容作废。
- **NR 时域防闪烁**：用户反馈效果不明显，顺路排查并修复。
- **执行方式**：不调用子代理，由主会话直接施工。
- **存档**：每个步骤完成都打存档标签，可以回退。
- **延迟**：内部链路必须保持现有的低延迟（这是相对 OBS、PotPlayer 采集的主要优势），每个引擎步骤都要对比延迟和提交间隔。
- **Bug**：施工中顺路排查并修复发现的 bug，逐条记录。
- **何时停下来问**：只有真正难以抉择时才停下询问，其余自行决定。
