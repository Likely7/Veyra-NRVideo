# Veyra 对照同类项目的改进执行方案

日期：2026-09-09。状态：方案已整理，以下新增改进尚未实施。当前 Phase 7 仍在进行，不以本文推进验收状态。

用户本次要求先暂停对“一卡、恢复、又一卡”的现场追查，整理对照方案。本文件依据已经固定版本的 GitHub 调查、当前源码和既有本机测试，不代表新一轮竞品实测。最近自然运行日志只有界面操作，未记录对应卡顿；具体后端与触发原因仍未确认。

## 1. 推荐路线

先把统计和帧调度做可靠，再降低 FRUC 互通成本和文件解码成本，最后补有证据的画质改进。保留现有 SR → NR → FG 顺序、两个 SR 后端和两个 FG 后端。

这轮最有价值的目标是：同样的画面设置下减少等待、周期性停顿和无效处理，保证每张有效帧按正确时间交付。不是通过增加缓冲、显示理论倍数或暗中降低 NR 分辨率让数字变好。

建议分成三批交付：

1. **第一批必做：配置隔离统计、轻量日志、有界处理与呈现调度、重置事件核对。** 先建立可比较基线，再逐项修改。
2. **第二批做实验后决定：FRUC CUDA 互通、文件硬解、重复 GPU 拷贝消减。** 只合入同源对照证明有收益且正确的方案。
3. **第三批按画质证据推进：运动置信度、NR/SR 运动稳定性、保护区域的 FG 语义。** 深度模型和预渲染缓存暂不加入默认运行路径。

导出完整性检查保持现状；开发短测不进入用户每次导出流程。每次测试调用最多 300 秒，累计不受“五分钟一轮”限制。

## 2. 对照项目：借鉴什么，舍弃什么

固定提交、来源链接与初次事实核对见 [GitHub 性能审计](../reports/GITHUB_PERFORMANCE_AUDIT_2026-09-09.md)。下表是对已取得材料的归纳，不是第三方性能排名。

| 项目 | 已核对的方法 | Veyra 应吸收的部分 | 不采用或不作推断的部分 |
| --- | --- | --- | --- |
| Magpie Experimental | 有界输出、输入节奏控制、卡顿后重新校准时钟；SR/NR/FG 分开；同帧对多子帧生成 | 明确输入、处理、呈现三种节奏；避免迟到帧成批追赶；保留生成有效性与 fence | 不复制实现；它也有 CPU 等待与切换卡顿。不能把其帧同步文档当成本机 GPU 加速证明 |
| NVEnc | FRUC 用 CUDA 设备指针，按目标 PTS 管理多个实例；RTX VSR 分档 | FRUC CUDA 互通试验；每实例历史与目标时刻明确绑定；按真实输出检查多倍插值 | 离线编码吞吐不是采集显示延迟；不照搬忽略重复回退标志的行为 |
| RTXVideoProcessor | GPU 解码帧池、GPU 颜色转换、VSR、GPU 编码，异步读包 | 文件模式硬解与有界帧池；减少 CPU 像素往返 | 其大容量队列不适合实时采集；GPU 内仍有 copy/synchronize；没有 NR+FG，速度不可横向套用 |

| video2dlssnr | SR → 光流 → NR → 合成；视频循环存在 CPU raw 输入/输出和等待 | 验证顺序、颜色与参数合同；观察线程重叠的用途 | 当前无明确许可证，不复用代码；不退回 raw pipe，不照抄“全链零 CPU 往返”宣传 |
| DLSS5-Feeder | 游戏内场景深度、估算运动、合成 DLAA 合同、资源互通 | 运动信任度与资源时序检查思路 | HDMI 没有游戏原生几何；不接 ReShade、不制造“等同原生”输入，不用合成 jitter 许诺恢复真实细节 |
| Zonnery/dlss5-nr-player | 已审计材料以 raw pipe、上传/回读和占位指导为主 | 作为最简调用方式的边界参照 | 不作为低延迟架构目标；固定 head 不等于完成新的逐项性能验证 |

## 3. 当前结构与真正需要改变的位置

增强图的顺序已经合理，现阶段不为猜测重排算法：

```text
文件 / 图片 / 采集
    → 颜色与时间戳解析
    → SR：DLSS 或 RTX Video（可关闭）
    → NR：实时内部尺寸或原生尺寸（可关闭）
    → FG：DLSS 或 FRUC（可关闭）
    → 播放器字幕 / OSD
    → 呈现或现有导出 sink
```

NVOF 与置信度按各消费者的资源和坐标合同供给；FRUC 使用自己的内部光流，不能假定可直接复用 NR 的 NVOF 结果。

当前 `EngineController` 同一循环中先处理，再等待整批生成结果，按 PTS 等待并呈现各子帧，最后读取下一源帧。底层有 command slot ring，并不代表这些工作已经充分重叠。FRUC 还需 CPU 提交确认；完整 reset 会停止并新建 worker。

目标结构是“同一个增强图，有界资源，多种来源调度”：

```text
采集回调 → latest mailbox（1） ┐
文件解码 → 有界帧池 / 背压     ├→ 图提交 → 有界待呈现批次 → 按 PTS 呈现
图片单帧 → 无时序处理         ┘       ↑             │
                                    └── fence / lease 回收
```

先做单一引擎所有者下的事件循环：GPU 提交、完成轮询、呈现截止时间、控制命令都可推进，不在整批子帧的等待中停止读取来源。若测量仍证实 CPU API 长时间阻塞，再将受影响的提交或呈现拆为明确所有者的线程；不是直接让多个线程并发调用同一个 graph。

资源上限必须先按现有 slot 和消费者 fence 算清。第一版待呈现队列最多保留一个尚未消费完的源帧批次（4X 最多四项），生产方拿不到安全空闲 slot 就背压；不为凑并行扩大 A/B/C history，不把逻辑队列长度当作实际资源池峰值。

## 4. 第一批：必须修正的基础

### P0-A：统计按真正应用的配置隔离

**证据：** 当前 TimingWindow 保留 1200 个样本，多个统计跨设置变化；NR 表盘只测 NR。用户之前开 FG 后 20ms→6ms 的一次异常已证实是隐藏页面串改 NR 尺寸，该设置缺陷已修，不能再次把它当作未知管线加速。

**实施：**

- 每条样本绑定 session、实际 applied revision、reset epoch、源帧号及批次号。异步完成的旧样本不混进新配置。
- requested 配置仍在应用中时不重置成“新配置已测”。回滚按实际生效 revision 归档。
- 配置、来源或尺寸改变时重建短窗口；预热单列，不删去卡顿时段。窗口同时设时间界限与容量上限。
- 日常模式保持简洁；专业模式直接显示输入 fps、源处理 fps、有效生成 fps、提交 fps，以及真实 SR/NR/FG 尺寸与后端。
- SR、NR、FG 阶段耗时分列；FRUC 当前指标标明包括队列等待/提交区间。GPU 时间与 CPU 等待不重复相加为“总延迟”。
- 无样本显示“未测”；Present 调用数只叫提交帧率。物理显示帧率与 HDMI→屏幕延迟仍须外部测量。

**验收：** 高频切换 NR 原生/实时、SR 后端、FG 开关和倍率，旧 GPU 完成回调不得污染新窗口；应用失败回滚仍显示实际配置。源 15→4X 的显示标签能分别表达源 15、目标 60、实际有效生成及提交速率。

主要位置：`src/engine/EngineController.cpp`、诊断快照结构、`apps/veyra/ui/AppShell.cpp` 和 GPU 指标聚合处。

### P0-B：把逐帧日志开销移出关键等待路径

**证据：** `src/base/Log.cpp` 每次写日志持锁并 fflush，当前逐帧有多条记录。存在开销不等于已证明它是主要瓶颈。

**实施：** 固定容量的结构化记录缓冲，后台批量写出；错误、设备丢失、NGX/NVOF/HRESULT/SEH、配置事务和 reset 证据保留。正常 UI 用低频摘要，详细追踪按需开启。缓冲溢出计数和故障尾部必须可追溯，不能静默丢掉失败码或无限增大队列。

GPU timestamp 仍异步回收，不能为写日志增加 GPU fence 等待。分位数不再在每帧重复复制并排序长窗口，改在低频快照时计算。

**验收：** 同配置 A/B 比较 CPU 提交时间、日志队列峰值、长间隔事件与源丢帧；故障注入仍能留下真实失败和配置身份。若没有可重复收益，不宣传 FPS 提升。

### P0-C：有界处理与呈现解耦

**借鉴：** Magpie 的节奏和有界队列原则；实现仍遵循 Veyra 单一所有者、资源 lease/fence 合同。

**实施：**

1. 将批次就绪、源读取、图提交、下一呈现截止时间拆成可推进状态；等待显示某个子帧时，允许提交资源足够的后续源帧工作。
2. 生成有效性在真实完成后判定；无效、过期、被取消的生成帧分别计数。不能以 Present 次数冒充真实生成。
3. 采集保持 mailbox=1，迟到时舍弃已经没有显示价值的生成帧，不瞬间追赶全部欠帧。真正源间断仍触发统一历史 reset。
4. 文件不丢源帧，保留音频主时钟、PTS 和有界背压。持续无法实时运行时明确提示，由用户选择减小增强负载；不靠改 PTS 或暗中丢帧隐藏问题。
5. seek、暂停、模式切换、resize、source switch 和 device lost 取消旧 epoch 的呈现；GPU 未完成的纹理必须等消费者 fence 回收，不能直接重用。
6. 普通呈现迟到与源内容间断分别记录。时钟校准不能伪装成新的素材序列，也不能用“清零 lateness”掩盖持续积压。

**验收：** 真实源序号/PTS 不混乱、无跨 epoch 呈现、无纹理提前覆盖；固定资源上限，A/V 不退步；同负载下提交间隔 P95/P99、最大间隔、过期生成率与捕获丢帧能重复改善。

### P0-D：重置成本与重复触发核对

**证据：** FRUC fresh worker reset 确实有启动成本；“掉帧→重启→更多掉帧”只是已知风险，目前没有对应用户卡顿的日志证明。

**先做：** 每个 reset 记录原因、源序列断点、epoch、排空/停止/启动/首对恢复耗时；检查同一个源边界是否被多个标志重复处理。一次边界合并为一次原子 reset，不能跨新的间断继续使用旧历史。

**再做：** 轻量 reseed 只作为独立实验，与 fresh worker 在切镜、PTS 回退、丢帧、重复帧后连续多个输出做像素和 PTS 对照。FRUC 的 skip-warp 不直接视为清空全部历史。

若轻量路径不能证明正确，保留 fresh worker。持续过载可提出用户可选的低倍率/暂停 FG 策略，但不能自动改用户手动配置，或无提示地把开启状态显示为已生效。

## 5. 第二批：超分与补帧的成本改进

### P1-A：FRUC CUDA 互通试验

NVEnc 的结构证明多实例、按 PTS 调用的路线有参考价值。我们目前 4X 使用三个实例，不是 SDK 内置“一次推理出三帧”；不要承诺改个资源类型就获得游戏 MFG 的复用能力。

在保留隔离 worker 的前提下，试验同 adapter 的 D3D12 共享资源/外部同步 → CUDA 可接受的设备资源 → FRUC → 共享输出。先确认 SDK 对布局、pitch、格式、CUDA 上下文和外部同步的实际要求；映射后若仍需设备内复制，也必须计时，不能称完全零拷贝。

拆分测量父进程拷贝、IPC 确认、SDK 调用、GPU 就绪与输出回收。在同尺寸、格式、素材、NR/SR 设置下比较现有 D3D11 worker 与 CUDA 候选。RGBA/NV12 的颜色差异另做检查，不把换成低精度格式后的速度当作同等画质胜出。

**建议进入产品的条件：** 至少三次短测均改善关键路径，收益大于本机运行波动，PTS/有效生成率/画质/重置可靠性无退步。预先将“阶段 P95 下降至少 10%”设为试验收益目标，不是现有门禁或必达承诺；若未达到，保留候选报告并停止扩建，不合入没有收益的复杂度。

### P1-B：文件硬解与 GPU 帧池

优先接通同适配器 D3D12VA 可用路径；若依赖能力不满足，再比较明确的 CUDA 互通候选，不同时造两套主解码系统。借鉴 RTXVideoProcessor 的帧池和异步读包思想，但采用小型有界队列和用户控制命令可取消的背压。

H.264/HEVC 硬解帧携带颜色、时间戳及 GPU 生命周期进入共享图，避免解码后整帧回读再上传。软件回退明确显示原因，保持可用。比较 CPU 占用、decode 时间、上传量、总吞吐与首帧/seek 行为。

**边界：** 原始 YUY2 采集不需要 H.264/HEVC 解码，这项主要改善文件播放；不保证解决当前采集卡顿，也不改变 NR 本身约 23ms 的原生 4K 代价。MJPEG 是否有可用硬解另查能力，不作默认承诺。

### P1-C：减少重复工作，保持处理尺寸诚实

- 核对原图、SR 底图和比较输出的重复保留是否能改为 lease 引用或按需复制；按住原图、分屏、截图、UI 保护必须仍对应同一源帧。
- 只在源身份和功能合同证明可跳过时缓存工作；不能把窗口重绘等同新源帧，也不能把静态重复画面冒充新增内容帧率。
- 避免无效的中间颜色转换；颜色、parity、range 和 resource state 检查优先于融合 pass。
- 用同源平移、遮挡、文字与纹理比较 DLSS SR 和 RTX Video SR 各档；保留用户选择。SR 低档+实时 NR 是有本机数据支持的实时候选，不擅自改成所有素材的最佳默认。
- 暂不改成 FG → SR → NR：那会提高后续高成本 pass 的调用次数，还会改变历史和画质合同。

## 6. 第三批：把上一版画质方案接续起来

上一版 [画质优化方案](QUALITY_OPTIMIZATION_PLAN_2026-09-08.md) 是历史起点，不能将其中“待实现”原样重复施工。依据 WORKLOG 与各专项复核：

| 原计划方向 | 当前已有成果 / 边界 | 本轮后续动作 |
| --- | --- | --- |
| 输入尺寸、奇数尺寸、颜色与预览 | 已有分块、尺寸/颜色/缩放专项修复与证据 | 性能优化后做针对性回归，不重写输入体系 |
| SR 参数与运动合同 | 已做方向、缩放、重建与运动响应实验 | 做自然运动的同源 SR 后端 A/B；空间更清晰不能掩盖时间闪烁 |
| 手动 UI / 字幕保护 | 已有保护区域、羽化、时序样本验证 | 保留；明确 NR 保护与 FG 插值保护不同，烧录 HUD 不能宣称完美分离 |
| 私有 UI 资源合同 | 部分试验未达到预期，旧 UI correction 开关不能当自动识别成功 | 不为追宣传强接未知合同；实验标识保留 |
| 运动置信度 | 已实现 cost、出界、亮度回投等门控；切镜/边界有专项验证 | 用遮挡、粒子、细线自然素材找失败，再局部改进，不全帧加重计算 |
| 双向光流 | 已有独立实验，尚未成为默认质量路径 | 先比较 A/B 两帧双向检查的成本与收益；需要 C 的额外验证明确计入 lookahead，不当免费未来帧 |
| 深度 | NR/SR/FG 已有响应试验，未证明引入默认深度模型有足够收益 | 暂不加入默认路径；只在明确失败场景出现可重复收益后考虑可选 Small provider |
| 视频专用 SR / FRUC | 已接入可选后端，并有实际调用和短测 | 现在做性能、节奏与自然画质对照，不重复“开始接入” |

质量验收分开记录：清晰度、时间闪烁、遮挡伪影、文字变化、有效生成率。FRUC 有返回成功但全部 repeated 的已有样本，必须继续计为没有有效插帧；不能拿 API 成功代替画质通过。

## 7. 统一对照方法与执行次序

### 7.1 基线

先记录当前源码差异、EXE/worker/runtime 身份和实际 applied 配置，保留现有未提交改动。每个实验用独立 run-id，不覆盖旧日志。第一批修改前后使用同一素材、适配器、输出尺寸、显示方式和电源环境；GPU 测试串行执行。

优先使用可重放文件：1080p60、1080p15、4K18。15fps 用来核对 4X60 的低源帧率场景；4K18 对应当前采集卡实际公开模式，不虚构 1440p30。最终由用户实卡确认输入间隔、音频与体感。

先测原图、仅 NR、仅低档 VSR、低档 VSR+实时 NR。然后在同一基础上对比 DLSS/FRUC 的 2X/4X；3X 做正确性与中间成本核对，不把所有设置做成无意义的组合爆炸。原生 NR 与高档 SR 作为成本对照单列。

每个新方案先一次 10–30 秒窄测；出现收益后才做三次 60–120 秒比较。每次完整调用硬上限 300 秒。切换/重置/故障窄测另开，不把预热和故障恢复混入稳态中位数，也不从报告删掉它们。

### 7.2 必须记录的证据

| 类别 | 指标与用途 |
| --- | --- |
| 身份 | 输入 hash、配置 revision、实际处理尺寸、后端、EXE/runtime/worker hash |
| 来源 | 收到/处理/丢弃源帧数、源间隔分布、已知内容变化率与名义 fps 的差别 |
| 生成 | 真实有效子帧、SDK repeated、无效/过期/取消数、各子帧 PTS |
| GPU / CPU | 各阶段 P50/P95/P99、CPU 解码/提交/等待、IPC、日志写入与分位数计算 |
| 呈现节奏 | 提交间隔分布、最大间隔、目标 deadline 偏差、连续卡顿事件的时间轴；全部标明非物理扫描 |
| 生命周期 | reset 原因/次数/耗时、epoch、队列/slot 峰值、显存峰值、失败码与设备丢失 |
| 整体限制 | A/V 漂移、源处理吞吐；用户实卡体验单列；温度/频率/功耗与日志时间对齐 |

可将“有效稳定片段中提交间隔超过目标输出周期两倍”作为诊断事件定义，但必须同时标出源重复、SDK 回退、切镜和显示刷新率，不拿这一个阈值机械判画质。没有足够有效样本时 P99 标未测。

### 7.3 如何判断软件收益与算力不足

源 60fps 的到达周期约 16.7ms；源 20fps 为 50ms；源 15fps 为 66.7ms。20→4X80 的目标输出间隔是 12.5ms，不要求把 SR+NR 对同一源帧执行四遍。既有 FRUC 2/3/4X 的 9.22/18.36/27.13ms 是含等待的阶段区间，不可当作纯插帧核耗时。

- GPU 阶段成本相近，而排队、迟到和长间隔减少：支持软件调度改善的结论。
- 同依赖链总工作持续超过源到达预算且没有可用重叠：该配置无法保持实时，需要用户选择较低负载；不能只看 NR 单阶段。
- 平均吞吐够但间隔长短交替：重点检查呈现节奏、SDK 回退、reset 与突发等待。
- 更平顺但采集帧年龄或音画延迟显著增加：不能作为低延迟采集方案的成功。

并行阶段不要简单相加，阶段 P95 的和也不等于整条链的 P95；用同一批次时间轴和实际稳态输出验证。

## 8. 暂不做的项目与原因

- **默认每帧深度模型：** 当前收益证据不足，新增推理和显存负担确定存在。
- **常驻自动 HUD 检测/OCR：** 不能保证烧录 UI 分离，先保留已验证的手动保护。
- **秒级缓存或无限预取：** 不适合采集低延迟；文件预渲染仅保留为将来主动操作。
- **并行接 Streamline、游戏注入或替换私有 DLL：** 不解决已知调度问题，会引入新的接口与生命周期变量。
- **删 reset、删 fence、直接复用在途纹理：** 可以让数字短暂好看，却破坏正确性。
- **默认自动降档/4X 自动变 2X：** 当前设置实时生效的语义应保持，先显示超载原因；自动模式需要独立产品决定和滞回设计。
- **加重导出完整性检查、先建议更换显卡：** 不符合用户约定，也没有足够依据。
