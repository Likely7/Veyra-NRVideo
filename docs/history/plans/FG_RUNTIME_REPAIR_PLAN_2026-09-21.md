## 1. 结论与承诺边界

建议替换补帧的执行、资源交接和呈现协调层，保留现有 NGX / XeSS 算法调用及
30/40 系兼容实现。先交付可验证的 2X，再覆盖 DLSS 3X/4X/6X 与 XeSS 3X/4X。
Veyra 的 XeSS 最高 4X，不存在本方案要修的 XeSS 6X。

当前不能诚实地承诺“90% 解决所有显卡、所有负载”。已有证据同时包含软件耦合、
预算拒绝与恢复开销，以及当前串行执行超过源帧周期的情况。重写的可兑现目标是
消除软件造成的额外损失，证明同质量、同倍率下的有效输出与节奏改善。
RTX 5070 上通过不代表 RTX 30/40 通过，也不能保证 3060 跑满 4K NR + 6X。

不新增固定缓冲延迟、不自动降倍率、不降低 NR/SR 质量或内部尺寸、不增加隐藏
源帧丢弃。不将重复帧、SDK 调用次数或提交 FPS 当成有效运动帧或屏幕实际刷新率。
已有实时过期处理继续如实计数；连续音频、媒体一倍速和导出完整性保持。

本方案收敛并替代旧收尾方案的 P1/P2 调度施工细节，P3-P6 等其他功能状态仍见
[原收尾方案](FG_STABILITY_COMPLETION_PLAN_2026-09-21.md)，本轮不扩展修改它们。

### 历史方案去重

以下方向已经有实际 A/B 结果，未取得可重复收益或出现负收益，已从本方案的
待实施范围删除：同组 GPU 成本估算器、去掉 Present 清屏、光流历史复制、把
原生光流尺寸直接交给 DLSSG、提高图形队列优先级、XeSS 只保留一组 pending
源帧、NVOF 与 Video SR 重叠、全局取消 DLSS admission，以及固定等待、盲目
增加队列、无条件接纳晚到生成、简单 CPU/presenter 拆线程或拆 owner。完整数据
保留在 [实验索引](../reports/FG_EXPERIMENT_INDEX_2026-09-21.md) 和对应原始实验记录中；
后续不得把这些方向改名后重复尝试。

“XeSS 真实源时间提示”是唯一保留的性能候选之一：已有吞吐收益，但仍需完成
逐帧节奏、资源生命周期和图像对应验收，不能把它写成已完成修复。当前真正未
解决的边界是 guidance、HDR 参考图、描述符、allocator、状态回读和 backbuffer
的完整资源租约，XeSS 匹配 Present 后的 provider 退休，以及历史有效性、已提交
状态和显示机会的分离。这些先做正确性验证，之后才讨论性能。

| XeSS Present 内部等待会阻止同一 owner 继续提交 | `VideoPresenter.cpp`、`XessPresenter.cpp`、`XessPacing.cpp` | 需区分可提前提交的工作与真实 GPU 依赖 |
| XeSS 首子帧调度入口存在未完成 fence | 保留的 351/351 次入口，前段平均 8.465ms，后段约 3.815ms | 前段不是纯睡眠或纯 GPU 运算，不能删除安全等待 |
| XeSS 源时间提示有部分收益 | 同条件重负载源提交约 40.03 -> 52.23/s，持续测试 52.09/s | 候选仍有约四分之一小于 1ms 的 SDK 输出间隔，未验收 |
| DLSS 当前串行路径有实际吞吐压力 | native NR 6X 完整组均值约 18.07ms；真实超分 + NR + 6X 约 22.92ms | 60fps 的 16.667ms 周期要求缩短关键路径；改期限无法补足 |

DLSS 重负载既有 `baseline/sr-nr-dlss6/result.json` 的 graphSubmit P95 为
1.663ms、slotWaitMs 为 0。更早原生输入审计中，FG 各调用之间的 GPU 时间空隙
合计平均仅约 0.083ms。因此，不能将 DLSS 的主要亏损归因于 CPU 命令槽等待，
也不能承诺搬线程或合并几次提交就能追回数毫秒。

18.07/22.92ms 是当前实现的测量范围，不是不可优化的纯计算下限。若完全保持
串行，要进入 16.667ms，整组时间分别约需减少 7.8% / 27.3%，还未计未覆盖开销。
当前没有证据支持通过重叠追回这段时间；GPU 平均占用与功耗也不能单独回答关键路径问题。

文件重负载旧样本中，DLSS 4X/6X 约 132.85/135.93 次提交每秒，分别有
295/361 组与预算拒绝、播种相关的 real-only 输出，生成后过期计数为 0。
这支持追查补帧前的决策和连续性，不支持把已生成后的丢弃当作唯一原因。
相关计数有包含关系，不能相加。样本范围见原始结果，非本轮新跑分。

最重要的反证：取消 admission 以前已使一组采集测试约 204.10 -> 184.76 次
提交每秒，源接纳率下降、生成后过期增加；文件测试也有约 59fps、1620 张过期。
本次不再把无条件生成、取消期限或放大队列当作新方案。

## 3. 要重写的边界

保留 `FrameSource -> EnhanceGraph -> FrameSink` 三入口共享架构、NR/SR/光流算法、
颜色合同、字幕后合成和导出处理。以下是建议的职责，不要求机械照此新建所有文件。

| 职责 | 最小改动范围 | 必须保留 |
| --- | --- | --- |
| 帧输入及资源租约 | 现有 FrameBatch/FrameLease、EnhanceGraph 输出边界 | epoch、revision、真实 PTS、源序号及资源身份 |
| 实时执行协调 | 保留现有 owner；只修有证据的资源退休和状态交接 | 文件音频时钟、采集容量 1 mailbox、现有最多 2 个在途源批次；不以拆线程/拆 owner 作为性能方案 |
| DLSS 执行适配 | EnhanceGraph 的 FG 调用段、FgRecoveryBudget 和发布接口 | 直接 NGX、2X-6X、逐输出有效性与现有兼容补丁 |
| XeSS 呈现适配 | VideoPresenter、XessPresenter、XessPacing | 代理交换链、原生依赖等待、2X-4X 与提供方资源合同 |
| 生命周期控制 | open/seek/pause/resize/switch/close 的事务交接 | UI owner、原子历史 reset、GPU 消费完成后释放 |

### 3.1 不可变输入与双向资源交接

每个已接纳输入明确携带 session/epoch/revision、A/B 源身份及 PTS、settings 快照、
颜色空间、尺寸/subrect、motion 前一帧身份、reset 原因、所有资源租约与 ready fence。
呈现线程不得回读正在修改的 graph 全局状态或当前 UI 设置来解释旧帧。

必须覆盖彩色、motion、depth、HDR 基底/参考图、映射纹理、描述符、allocator、
状态回读区及 backbuffer。优先复用现有双缓冲；单份可变 guidance 若不能满足
生命周期，使用受同一在途上限约束的资源槽，并单列新增拷贝/显存成本。
不能只把彩色纹理放进 shared_ptr 就认为异步正确。

必须形成如下跨队列依赖：

```text
增强队列: 写入 B -> Signal ready(B)
消费队列: Wait ready(B) -> 读 B / 生成 / 呈现 -> Signal consumed(B)
资源复用: Wait consumed(B) -> 下一次覆盖同一槽
```

XeSS 的 consumed 必须覆盖匹配 Present 中提交的 provider 工作，不能使用
Present 之前的 blit fence。根据 Intel UNTIL_NEXT_PRESENT 合同及 Magpie 实现，
应在匹配 Present 返回后向 SDK 初始化使用的队列 Signal，再由生产队列 Wait
后复用。CPU 返回本身不是 GPU 完成；不得逐帧排空 SDK 内部队列或跳过 fence。
当前同线程/同队列的实现并未因此被证实存在提前复用错误。

完整跨队列资源状态、NGX parameter block 与 Feature owner 也必须明确。
同一个时域 FG Feature 的 A/B 调用保持有序；禁止多线程同时 Evaluate 同一实例。
命令槽数量和在途帧数量分开管理，不能靠增加真实画面排队掩盖资源退休问题。

### 3.2 已排除的调度优化

简单的 CPU 提交/呈现拆线程、拆 owner、逐输出发布，以及 `FG(B)` 与下一批
`Enhance(C)` 的并行重叠，均已在本项目的实验路径中验证为无收益、负收益或缺少
可证明的关键路径缩短。它们从待实施方案删除，不再新增 presenter worker、独立
FG queue 或“先发布再等待”的性能改造。

这不删除 3.1 的资源正确性要求：若后续出现明确的提前复用、provider 退休或
状态交接证据，只修对应租约和 fence 合同；不能借资源修复之名重新引入并行重叠。
既有数据也已经排除了“删掉约 0.083ms 的 FG 调用间隙就解决 6X”这种解释。
没有新的 GPU 关键路径证据，不把高倍率稳定满速写入交付结果。

## 4. 两个后端各自修什么

### DLSS：先减少真实亏损，再修可证实的误判

保留全组倍率、各子帧位置、frameId、reset 及 NGX 参数合同。
将历史状态与显示状态分开记录为：历史缺失/有效、已提交/待完成、有效但显示
机会过期、被预算拒绝、真实输入断点。已提交有效但未显示的帧不应仅因显示
丢弃而重置算法历史；真实 Skip、seek 或输入断点则不能免掉必要的恢复。
现有代码已满足的行为保留，不将此规则自动算成已发现的新 bug。

调度从整组截止时间临时判断，改为显式的源批次工作计划：在提交下一批重负载
前明确当前批次的 FG 工作、真实首/尾截止时间和资源占用。已接纳 FG 不被下一
批可推迟的重工作无意挤到后面。初期保留原有准入判断，先验证新执行顺序。

之后只针对时间线能证明的重复计费、已完成工作仍计入队列、过期估计或错误
截止时间修改 admission。拒绝日志配合实际完成/等待数据才能形成疑点；未执行
的整组没有真实 GPU 成本，不能仅凭估算就宣布“误拒”。必要的受控诊断生成
必须有界，不能把全局取消 admission 放回产品。

恢复状态机的验收重点是拒绝后是否出现不必要的重复播种、负载解除后多久恢复
有效插值。恢复成本必须计入计划，不能每次拒绝都假定下一组可免费恢复。
已失败的同组成本估算器不重做。即使输出决策改善，也不得隐藏源帧跳过率。

### XeSS：时间来源、标记和资源依赖一起对齐

先完成现有真实源时间提示候选的图像/生命周期验收。它对重负载已有重复收益，
但 52 源帧/s 和明显突发尚不足以称为稳定 4X。连续 A/B 用真实 PTS 间隔；断点、
未知或历史不匹配时按 SDK 合同 reset / 采用允许的默认值，不硬填 16.667ms。
`frameRenderTime=0` 是 SDK 允许值，当前传 0 本身不是 API 错误。

Intel XeSS 3.0.2 文档明确：启用 FG 必须启用 XeLL；Sleep 需先于该帧所有标记，
每帧一次，XeLL ID 必须与 PresentId 相同。不能通过关闭 XeLL 或删除 Sleep 来
宣称优化。应用可选帧同步关闭，也不能解读为已取消提供方必需的依赖管理。

只有一个插值呈现节奏的 owner。文件真实 PTS/音频时钟继续决定媒体进度，
不能用处理帧率取代；XeSS 控制自己的生成帧，不额外叠加应用逐子帧 Sleep。
需要检查现有候选受下游阻塞反馈影响的位置，不假定现状每处都在重复限速。

若解决资源/提交阻塞后仍存在“输入及时可用但 SDK 期限异常”的证据，再移植
Magpie 的源周期及 timestamp 策略。保留原生 anchor 和 fence；禁止把资源等待
全部从周期扣掉、靠压缩期限把多张输出挤在一起，或重锚定文件音频时钟。
正常 VSync / 自定义限帧造成的取舍必须单列，不冒充无上限模式的回归。

## 7. 验收标准

以下数字是建议的接受门槛，不是已经测得的改善或成功概率。
每次固定片段、效果顺序、内部/输出尺寸、窗口和 monitor 尺寸、运行库、驱动、
同步/限帧模式。XeSS 当前保留大交换链尺寸，不能拿不同像素负载与 DLSS 排名。

### 指标

同时报告输入接纳、真实源覆盖、有效插值、SDK/应用提交、实际可测的系统显示
事件、全段 P50/P95/P99/max 间隔、突发比例、帧龄、过期、恢复和 GPU 关键路径。
CPU ready 观察值是上界；跨 CPU/GPU 时钟必须校准。不要把各阶段 P95 相加。
XeSS SDK-return 间隔不等于 scanout；物理显示延迟没有相机/硬件证据就写未测。

以下逐帧节奏门槛只适用于能观测到的逐输出事件，同一后端必须用同种事件比较。
如果只能观测到一整组的外层 Present 返回，就不能据此推算组内各帧均匀。
生成/提交侧和系统显示侧分别报告；超过显示器刷新率的目标不能作为物理显示
覆盖率门槛。缺少逐帧或显示事件时，分别标记未测，不用平均 FPS 替代。
所有负载均要求同种起止事件测得的 P50/P95 帧龄不超出基线波动，不能以新增
排队延迟换取节奏门槛通过；性能测试还须记录显存峰值和资源槽数量。

设源周期为 T，倍率为 M，目标输出周期 D=T/M。在固定源率、VSync 关闭、输出
不限制且工作量确有余量的稳态片段，建议门槛：

- 源覆盖至少 99%，有效运动输出至少目标的 95%；2X 与高倍率分别验收。
- 输出间隔 P99 不超过 2D；小于 0.25D 的追赶突发低于 1%。
- 120 秒内没有可归因于调度的持续 T 级空档；切镜/显式重置和输入自身停顿单列。
- 由观测证实、因不必要拒绝或反复播种造成的空档归零。未知项不能排除后算通过。

重负载未能满速的工况可接受部分优化，但不能标注“满倍率修复”：

- 对照至少两组交错 30 秒短测，改善超过基线自身波动；有收益再做 120 秒。
- P99 或长空档数至少改善 20%，其余尾部指标不退步；仅平均 FPS 增加不接受。
- 源覆盖、有效生成覆盖均不减少；P50/P95 帧龄不得有超出基线波动的增加，
  尤其不允许多排一帧换取平滑。比较同种输入时钟到同种结束事件。
- NR/SR 设置、guidance、色彩及清晰度等效；没有新增重复插值、错帧或果冻/拖尾。

独立测试已知轨迹/切镜素材检查帧身份和内容；真实视频检查快速转身、遮挡、
细线、文字及暗部。诊断抓帧与性能测试分开，正常产品路径不增加像素回读。
仅 SDK 有效标志或独特纹理 hash 不能证明运动时间位置正确。

### 覆盖与回归

先测 native 输入 / 真实 1080p -> 4K、FG 单开 / NR+FG / SR+NR+FG 中能覆盖
被改依赖的最小组合，2X 先行；再覆盖 XeSS 3X/4X 与 DLSS 3X/4X/6X、30/60fps，
以及 24fps 文件的媒体时钟回归。轻载通过后才运行重载，单次进程最长 300 秒，
watchdog 生效，构建和 GPU 测试不并行。

保留现有 `veyra_fg_sustained_tests` 和 `ui-fg-backends.py` 的产品链路测试；
新增有意义的资源/时序重放，覆盖随机 ready/Present 延迟、两批资源上限、
取消和 reset；它用于验证退休与历史边界，不用于重新证明 CPU/presenter 拆分
或并行重叠有收益，也不得用只验证自己新增常量的测试充数。

必须回归：后端/倍率切换、seek、暂停恢复、切镜、resize、DPI/跨屏、窗口中键
拖动、退出、输入断开、设备丢失、HDR、字幕和截图；共享图改动另做导出回归。
控制线程先停止新接纳并换代，provider owner 完成安全退休后再重建。不能在
持有 UI 锁时等待 Present/join，也不能取消作业后提前释放 GPU 正在读的资源。
无第二显示器或受影响采集卡时明确未测，不用视频通过替代实卡证明。

RTX 5070 负责本机完整验收；30/40 保留现有兼容调用，至少要求各一台实际
机器验证启用、2X、高倍率及持续播放。拿不到硬件结果时交付为“待实卡验证”。
不能用架构伪装本机当作 3060/4070 的性能验收。

## 8. 可行性判定

若资源与时序正确且未发现可消除等待，则记录为当前实现和运行时下仍未解决的
吞吐边界；不再默认开启已失败的重叠实验。只有新的关键路径证据支持时才归因为
GPU 运算或运行时内部限制；有限实验失败不等于证明硬件已无优化空间。
保持质量、倍率和低延迟时，不能据此保证连续均匀满速，也不能靠自动降级、
重复帧或新增排队伪装任务完成。此时停止该性能方向，交付已接受的独立修复
和明确配置边界，后续由用户选择。

这套方案的可信度来自每一步都能被同条件对照否证和撤回，不来自未经测试的
“90%”数字。完整重构也必须逐阶段证明比基线好，不能因改动大就直接替换正式版。
