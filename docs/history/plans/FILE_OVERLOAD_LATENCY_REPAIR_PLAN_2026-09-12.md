# 文件预览过载迟到与延迟口径修复方案

日期：2026-09-12。状态：方案，尚未实施。基线 main / 9383f3b，已发布0.0.5。用户要求根据4060日志给出修复方案；本轮只核查代码/日志并记录，不改产品、不构建、不发布。

> 后续更新：用户确认的主面板处理耗时、详情首项额外显示延迟已单独实施，见 `PROCESSING_METRICS_ICON_2026-09-12.md`。本方案预测选帧/过期原帧呈现等调度修改仍未实施。

## 1. 目标

保持现有音频连续与媒体时间一倍速，减少文件增强预览在过载时可以避免的画面迟到；让面板区分处理耗时、排队、画面迟到、音画时间线偏差。不得通过清零计数、移动时钟、暂停声音、丢PCM或自动降低用户画质制造“零延迟”。

实时采集/PS5仍是没有未来帧的输入，不把文件的提前处理办法硬套上去。导出、图片及暂停指定单帧仍完整处理，导出检查不加重。

P95来源/窗口不同，不能相加或从gpuReadyP95减算法P95推导GPU排队。decodeP95只测当前read调用，不证明完整解码管线延迟为0.428ms。音频lead使用已呈现覆盖区间终点，面板迟到使用原帧PTS，采样时刻也不同，不强行要求两者相等。

明确的代码缺口：
1. RealtimePreviewScheduling.h 的 previewCandidateExpired 只看 now > pts+duration，不看预计完成时间。源帧刚追到当前时间再做增强，完成时仍可能迟到。
2. 同文件注释仍称“只有一个in-flight batch，完成原帧必为最新”；实际Engine容量2，生成帧有过期判断，已完成原帧无相应新鲜度选择。
3. File enhancementDelayEstimate 实际为 max(0, audio/mediaClock - presentedFramePTS)，不是完整增强成本或严格测得开关增强的因果差值。
4. 每次跳帧会做soft history reset；用户日志反复reset=true。当前必须保留断点重置，不能为提高计数偷偷复用不连续历史；其性能/画质代价要纳入预测。

这些证明策略有不足，不足以断言4060的全部60ms都能消除。源码审查未复现用户负载。

## 3. P0：先把测量说明白

维持已有四个算法卡、曲线和底部布局，不增加一屏新数字：
- 本地视频曲线标题：画面迟到 · 平均；说明：相对正常播放时间，音频为参考时钟，非屏幕实测。
- 采集/PS5保留：增强额外延迟 · 估计；明确起点分别是实际decodedHost或采集callback，基线不足显示未测。
- 详情显示：原帧GPU执行、提交后等待GPU完成、GPU就绪后等待呈现、原帧迟到均值/P95、音频相对视频覆盖的偏差。执行时间与CPU观测等待存在重叠，明确不可直接相加。
- 未开启增强时不要把真实文件迟到强制写0：记录实际画面迟到；“额外增强延迟为0”的定义单独保留在对应估计中。
- 统计绑定session/revision和源帧身份。首帧、seek、设置重建、暂停、端点恢复分开标记；曲线缺失断线，不用0补点。
- 与当前音频设备时钟比较的结果不叫物理声画差；WASAPI/显示器/扬声器的实际输出仍需额外测量。

以一条抽样关联日志记录选帧时主时钟、源PTS/duration、预计就绪、提交、GPU就绪观测、Present返回和丢弃原因。常态最多每秒汇总/抽样，异常短环形轨迹按需导出；不逐帧刷完整日志，不引入像素回读或CPU fence等待。

## 4. P1：按预计完成时刻选帧

复用现有单GPU所有者和有界预览队列，不另造播放循环。

- 从同revision/尺寸/后端的已完成任务估计“新增一帧的完成成本”，计入必要颜色、光流、NR、SR、残差/输出及soft reset代价；可选FG成本独立。
- 排队工作与自身执行分开。用未完成任务及实测完成服务时间预测候选完成位置，禁止将端到端等待与GPU执行再次重复相加。
- 候选目标依据预计完成时刻的媒体时间选择；若源帧显示区间预计已过且有更合适候选，在上传/增强前跳过，优先选择覆盖预计显示时刻的帧。
- 文件可提前正常解码。跳过的是解码后预览增强机会，保持压缩参考链、PTS/序号真实；不得连续seek追帧。
- 预测窗口有硬上限和置信度/迟滞。启动/大设置变化先有限预热，不能靠保守P95不断向未来跳，吞吐够时仍逐帧呈现。
- 追赶解码循环限制单次工作量，定期回到呈现、seek、stop处理。遇到Waiting、EOF、无效duration、重复/非单调PTS按源契约处理。
- 不扩大现有GPU任务容量/纹理池；跨read持帧必须av_frame_ref/clone+RAII，不能保留借用裸指针。
- 音频不根据这个预测新增延时补偿。文件提前处理围绕音频时钟安排画面，避免两个补偿器互相追赶。

优先省FG再省原帧增强；30fps只能处理15fps时，输出PTS应均匀覆盖时间线，接近隔帧选择而非播放前半秒。

## 5. P2：去掉可避免的旧结果呈现

先审查LiveGpuScheduler的任务和租约关系，再扩展：
- 两个已就绪原帧中，旧帧已过显示区间且新帧在允许呈现窗口，直接选择更新的结果。
- 不能因“迟到”无条件丢弃唯一可用原帧，不能把尚未GPU完成的后续帧当作可显示替代；不能提前显示未来PTS。
- 原帧/生成帧以单调PTS呈现，去掉旧原帧时一并处理其生成帧机会，禁止时间倒退或FG端点错配。
- 跳过呈现不等于省下已执行GPU工作，分别计数；资源仍等实际GPU/consumer fence安全完成后释放。
- 无ready任务时保留上次已显示纹理，不伪造新帧率。EOF最后一帧、暂停查看、seek确认仍能完成。
- 调整需保留输出槽“仍被占用禁止覆盖”保护，不再引入旧seek崩溃。

这只能减少冗余旧结果，不能代替P1，也不保证把60ms压到0。

## 6. P3：音频、FG与实时源边界

- 保留现有连续音频；正常负载波动不调用Stop/Reset，不丢PCM、不变更媒体速度。
- FG预算使用修正后的准入截止时间，保留迟滞和有限恢复探测。检验不重新出现30→2X锁30、XeSS频繁启停或4X一阵卡一阵好的行为。
- 软断点继续reset必要时间历史；均匀选帧/减少不必要追赶可以减少突发重置，但不取消断点保护。
- 本轮不更改采集/PS5音频自动补偿算法，不给直播套未来帧预读。若共享呈现选择影响实时源，必须独立验证最新帧行为。
- 不自动切换NR实时/原生档、SR目标或后端；过载状态依然如实显示。

## 7. 验收与交付顺序

开工先Git存档和隔离分支。节点1测量/显示，节点2预测选帧，节点3就绪选择与回归，各节点更新本记录、WORKLOG并保存Git。

可重现故障测试优先：
- 60fps源、每源帧稳定约25–30ms处理成本：旧策略迟到可复现；新策略预计更及时且均匀跳帧。
- 30fps源、每帧约66ms：呈现约15fps但源PTS覆盖真实一秒，不能慢放成半秒；音频连续。
- 60→120只达到约110呈现：音频不等待目标FPS。
- 30/35ms波动、短GPU尖峰、成本升高/降低及NR/SR顺序切换：预测收敛，不长期追未来，不周期性停音。
- 正常4K30 NR＋2X、DLSS3X/4X、XeSS2X不退化；无需反复重新开功能才能恢复。
- 无音轨、静音、音轨提前结束、seek连拖、暂停单帧、EOF最后一帧、设置事务与端点恢复。
- 原帧/生成帧PTS不倒退；资源峰值和队列保持边界；无额外PCM丢弃/重置、无设备错误。
- 采集/PS5共享代码回归；导出帧数/时间戳/音轨沿用现有检查。

先用生产调度策略的确定性模拟验证，再做实际RTX5070 GPU与用户同源4060 A/B；模拟负载不能冒充4060结果。每个配置启动/预热后取稳态窗口。对比音频连续性、真实/生成呈现率、迟到mean/P95、丢帧分布、GPU成本与ready等待，不只比较面板数字。新方案若靠大幅额外跳帧换低迟到，应如实报告并评估是否值得。

建议局部检查通过后运行一次统一delivery gate，单次测试≤300秒。没有4060同源测试不写“4060已修复”；没有物理测量不写“零音画差”。具体迟到下降门槛先由确定性负载预算和旧版A/B建立，不能事后任意放宽。

本次方案无需新SDK/运行时，不发布0.0.6、不覆盖0.0.5资产。下一步唯一任务：实现P0关联测量并建立旧版可复现过载样例，再实施P1/P2。
