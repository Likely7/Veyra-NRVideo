# 连续音频与实时视频调度修复方案

日期：2026-09-11。状态：**已实施（隔离分支 `agent/av-scheduling-repair`，提交 `9885759`+`5bc91cd`）**。基线：0.0.4，产品提交 `cecf34e`；开工存档点 tag `checkpoint/av-scheduling-2026-09-11`（提交 `21ce5d3`，与 0.0.4 产品无 C++ 源码差异）。P0–P4 代码与本机（RTX 5070）回归完成：A/B 证明 0.0.4 音频策略在持续欠速断言上失败、修复后全过；采集生产算法按 §3.2 未改动，采集 XeSS 欠速门控本轮仅文件路径+单元覆盖。完整命令、证据与未执行项见 `docs/WORKLOG.md` “连续音频与实时视频调度修复”条。4060 实机复验、物理声画测量与长期稳定性仍待用户验收。

目标：播放或采集增强处理达不到请求帧率时，保持声音连续、媒体时间正常推进、视频延迟有界；短暂耗时波动不反复停声音。用明确的预览帧取舍处理算力不足，不以音频暂停掩盖欠速，不声称提高 NR 本身的算力。

## 1. 本次问题与证据

用户4060日志的主会话是60fps文件，DLSS2X的32个连续统计窗口平均推进51.45张源帧/秒、提交102.89张画面/秒；不开FG的一段也仅47.39张源帧/秒。依据及统计口径见 [4060诊断](../reports/RTX4060_AUDIO_UNDERRATE_2026-09-11.md)。日志没有逐次音频暂停事件，不将推断写成已测得的停音次数。

0.0.4 的 `AudioVideoContinuity` 在领先超过20ms持续100ms或领先达到80ms时暂停WASAPI，视频覆盖追上再恢复。它能容忍短暂抖动，但持续欠速仍周期性停音。此前回归中的“偏差有界、过载能暂停和恢复”不能作为本次连续播放通过条件。

必须分开三个指标：

| 情况 | 源媒体时间 | 音频要求 |
| --- | --- | --- |
| 60原帧＋50生成帧/秒 | 正常推进1秒 | 连续正常播放，不因不足120而暂停 |
| 55原帧＋55生成帧/秒，原片60fps | 仅推进约0.917秒 | 当前策略会停音；新策略必须纠正视频选择与工作量 |
| 30fps原片只显示15帧，但PTS均匀覆盖该秒 | 正常推进1秒 | 音频连续，代价为视频动作更不连贯 |

修复针对截止时间和媒体时间，不写成“FPS低于目标就切换某模式”。任何一秒统计窗口都有波动，120的请求不是声音开关。

## 2. 拟定产品规则与范围

本方案建议文件播放和采集预览默认采用“声音连续、正常速度、允许过载时少显示帧”。不新增自动切换NR画质、SR分辨率或后端；按用户选定画质处理被选中的视频帧，优先减少可选补帧工作。不恢复FRUC、AMD NR或增加新SDK。

原帧不足时按真实PTS取样，30→15应接近 `1、3、5…29` 或 `2、4、6…30`，而不是先播 `1…15` 再慢慢播放剩余半秒。实际选帧随完成时间变化，不保证固定奇偶。丢的是本次预览的增强/显示机会，不修改源文件，不随之丢PCM、音轨或字幕时间。

范围隔离：

- 文件实时播放：允许跳过过期或无法及时处理的预览原帧。
- 采集预览：保留现有容量1最新帧邮箱，在增强提交和呈现阶段继续抑制过期工作。
- 图片处理、单帧暂停查看：完成指定画面，不能因实时截止时间跳过用户要求的帧。
- 视频导出：逐帧处理、完整音轨及原有CFR尾帧政策；现有完整性检查保持原样，不继承预览的丢帧策略。

**与历史规则的关系：** `AGENTS.md` 实现纪律及旧产品规格有“播放器/导出不得丢源帧”。本方案提出仅为实时文件预览修订播放器部分，导出约束保留。本轮不改规则或产品；用户要求按本方案开工时，在实施首步同步这条明确范围，不能让后续Agent重新用旧规则恢复停音策略，也不能擅自将例外扩大到导出。

不增加第二套增强引擎。保留共享 `FrameSource → EnhanceGraph → FrameSink`、单GPU所有者、绝对路径加载、现有色彩与SR→NR→FG顺序。

## 3. 时钟和链路设计

### 3.1 文件播放：音频时钟推进，视频提前准备

音频解码、PCM队列及WASAPI线程继续独立工作。稳态以实际音频设备时钟映射的媒体PTS为主时钟；静音仍推进该时钟，不能将音量0视作没有音轨。无音轨文件使用单调主时钟；合法音轨结束后才切换到视频尾部时钟。

```text
文件音轨 → 音频解码 → 有界PCM缓冲 → WASAPI连续输出 → 实际媒体时钟
                                                        ↓
文件画面 → 有界预解码 → 选取将到显示时间的帧 → SR/NR → 可选FG → 按PTS呈现
```

- 打开和seek仍先对齐音视频媒体起点，允许有限预热与音频预填充；共同起点建立后，不能因普通GPU欠速调用音频Stop/Reset或反复移动音频锚点。
- 视频的目标呈现时刻来自原始PTS与该共同锚点。文件可以提前解码/增强，不能等音频已经走到该帧才开始全部GPU工作。
- 引入受限的提前处理窗口，初始按同设置下实测完成耗时估计，再依据当前队列修正；限制持有的解码帧、GPU槽位和可呈现结果数量，不把整个文件预解码进内存。
- 文件预处理耗时主要由启动预热和提前计算吸收，不能把每帧 `gpuNrP95Ms` 直接加成一个新的音频延迟；那会重复补偿并与主时钟调度互相追赶。
- 只因画面落后而调用 `holdForVideo()` 的正常播放分支移除；首帧/seek/明确暂停/端点恢复等显式状态另行保留。

### 3.2 采集卡：保留输入时钟映射，仅补偿软件新增等待

采集卡没有免费未来帧。持续采集音频与视频已经共同经历的输入延迟不得再补一次。

自动补偿沿用可验证的映射：

```text
M = 音频输入host时间 − 音频输入PTS
D样本 = 视频Present返回host时间 − 视频PTS − M
```

`D样本`包括软件中等待未来帧、增强和呈现调度产生的等待，但Present返回不是屏幕扫描时刻。按真实采集输入时间戳计算，不用目标FPS的倒数冒充实测延迟。

- 音频保持有界延迟缓冲，输出连续。现有采集重采样/时钟修正优先复用，先补诊断证明哪个分支导致停音，再修改。
- 视频通过最新帧与过期工作剔除维持稳定年龄；补偿器不负责吞掉无限视频积压。
- 自动补偿保留已有1500ms上限和2000ms总音频队列预算，本轮不再扩大。手动音频偏移及关闭同步设置仍有效。
- 输入端点中断、设备断开或源PTS跳变单独处理，不能归入正常NR波动。

### 3.3 小波动与大变化

建议初始参数作为待验证策略值，不能当作已测结果：延迟观测窗口约1秒，每100ms更新一次估计；围绕稳定目标保留±10ms死区。观测剔除暂停、seek、重建、失效epoch及异常时间戳，延迟毛刺不直接重锚。

文件的微小抖动优先由提前处理窗口和视频呈现截止时间吸收。采集端小范围时钟修正沿现有有界重采样实现，不能插入静音、截掉PCM块或改变音频PTS伪造连续。修正速率及最大比例必须依据实际听感/连续性测试确定并记录，不在本计划承诺某种变速无损或完全不可闻。

设置大幅变化导致延迟阶跃，允许一次明确的重新同步/短淡出；不必承诺重建NGX期间也绝无中断。新的稳定区间不得残留旧补偿。没有改设置的30/35ms波动不能走这个分支。

## 4. 视频选帧与提交策略

### 4.1 先省补帧工作

先测已经完成的源帧处理、FG及Present成本。预测使用相同后端、设置revision和尺寸的有效样本；剔除创建/预热异常。CPU提交时间、GPU执行时间、排队/就绪时间分开，不能相加重复计费。新配置样本不足时保守预热，再有限探测FG，不因缺样本永久关闭。

DLSS现有 `EnhanceGraph::FgAdmission` 是整对布尔准入，当前只在采集路径使用。文件预览也应在FG Evaluate提交前判断：这对生成帧是否仍有显示机会、是否会挤掉接下来原帧的截止时间。预算不足则跳过这一对的可选生成工作，保持正常源帧节奏。

3X/4X初版可沿用整批允许/跳过，不为省某一个子帧擅自改变SDK的multiFrameCount/index契约。按批次分散选择，避免一长段全补、一长段全关。若恢复FG需额外warmup，就必须计入实际成本；宁可在持续欠速时稳定少补或暂时不补，不能频繁开关反而更慢。

对已经提交且结果过期的生成帧，仍应跳过呈现；但另记“算完未显示”，不能把它算成节省GPU工作。所有被跳过结果仍等待其实际fence后回收，绝不能提前覆盖资源。

### 4.2 XeSS独立接入准入

XeSS生成发生在SDK交换链内，不能复用“引擎看见每张生成帧”的假设，也不能仅少调用普通Present来宣称跳过了SDK生成。

当前 `XessPresenter::tag()` 已调用 `xefgSwapChainSetEnabled`。实施时核对本机已固定SDK的禁用、重新启用、资源有效期与history要求，验证能否按选定帧/稳定区间临时禁用生成而继续真实原帧呈现。若逐帧切换收益或正确性不成立，使用有迟滞的稳定停用/恢复区间，不每帧重建交换链。

实际SDK生成计数、开关返回值、原帧进度分别记录；不以引擎Present次数乘2推算实际输出。恢复时按当前有效A/B输入重新建立FG历史。

### 4.3 原帧增强也处理不完

这时才跳过部分预览原帧的昂贵增强。按主时钟、完成耗时预测和PTS选择将到呈现时刻的候选，确保画面内容持续覆盖现在播放的位置。算法不能简单地“每次取文件下一个帧”，也不能只处理每秒前半段。

文件解码保持编码参考关系和显示PTS排序。先正常解码，再丢弃不再需要增强的输出帧；不得随意丢H.264/HEVC压缩包，否则参考帧可能损坏。初版不使用不断seek到关键帧的粗暴追赶。若解码本身长期低于实时速率，单靠GPU前丢帧无法解决，必须单列“解码不足”，不能算整体修复通过。

建议新增最多3个持有引用的解码候选，GPU继续使用现有固定command slots和严格有界的结果池；解码器内部参考帧单独统计。解码所有者可为单独CPU worker，所有D3D/NGX调用仍归唯一GPU所有者。`MediaFileSource::read()` 返回借用AVFrame，跨调用必须clone/ref并用RAII释放，不能把悬空裸指针放入队列。

帧取舍规则：

1. 已过显示窗口且有更合适候选：在上传/颜色/SR/NR前跳过。
2. 还有时间且预计能完成：提交必要原帧处理，再评估可选FG。
3. 完成后发现过期：有更新的就绪画面时淘汰旧结果；没有更新结果时保留上一显示并选择下一次可完成的机会，不能出现“所有帧都过期所以永远黑屏”。
4. 固定欠速时尽量形成均匀的有效显示间隔，处理恢复后平滑回到全源帧速率，不回放积压旧画面。

源PTS、序列号及duration保持真实；不能重编号成连续15fps后说未丢帧，也不能把重复保持画面计作新处理/生成帧。

### 4.4 时序历史与降帧画质

跳过源帧会改变运动估计的时间跨度。SR/NR/flow/FG必须看到一致的实际源序列与PTS；不能给跨两帧的运动输入继续配一帧时间。

初版对预览源帧跳过按显式历史断点处理，复用统一reset coordinator，保留资源lease/fence。只跳生成工作而原帧连续时，按现有 `fgHistorySkipped_` 恢复FG，不顺带重建全部增强功能。软历史reset不等于反复销毁/创建Feature。

持续30→15可能频繁失去时序历史，降低NR/FG效果。必须纳入动态画质和吞吐验证，不能只测声音。如果要优化成稳定采样节奏下保留历史，必须另证真实PTS跨度、flow匹配与SDK行为，并将其定义为明确的新采样契约，不能偷偷忽略断点。

## 5. 状态与异常恢复

| 状态/事件 | 音频 | 视频及历史 |
| --- | --- | --- |
| 打开/seek预热 | 有界预填充，首个有效共同锚点前不播放 | 清旧队列，重新定位；处理负起始音频PTS、B帧和非零起点 |
| 稳态或算力欠速 | 连续，普通GPU等待不能Stop/Reset | 补帧准入、按时选帧、过期淘汰 |
| 用户暂停/恢复 | 显式暂停，恢复重新建立共同时间关系 | 暂停截图/单帧仍准确；不应用连续播放丢帧 |
| 设置重建 | 可一次有界淡出/重同步，报告原因 | 合并最新设置；隔离旧revision；失败按现有回滚 |
| resize/全屏/显示模式 | 普通短重排不反复停音；必要资源重建明确记录 | 只失效必需资源与历史；防跨旧epoch提交 |
| 音频端点失效 | 真实失败与恢复状态，不假报声音连续 | 冻结共同时钟或受控恢复，不使用失效音频时钟无界推进 |
| 音轨先结束/无音轨 | 正确切换单调时钟 | 保留媒体尾段，不因音频EOS卡死 |
| 设备丢失/源切换/PTS断点 | 清理并重新锚定 | 取消旧任务、等待fence、全历史reset |

当前4060日志还出现首个文件音频起点 `-1.3ms`、首张原帧直到切换文件都未呈现的现象。未确认因果，本轮把负PTS/音频起点纳入启动回归，不能因为只修欠速而遗漏首帧死等。

## 6. 用户可见状态与诊断

复用专业模式“实时处理状态”，只补必要信息，不在本轮大改布局或新增一排调参选项：

- 请求输出：例如120fps；实际源帧处理、有效生成帧、呈现提交分别显示。
- 正常播放速度：根据媒体PTS/墙钟实测，例如1.00×，不要用实际处理FPS/源FPS直接冒充播放速度。
- 状态：“正常”“补帧预算不足”“预览已跳帧”“解码不足”“正在重新同步”。不擅自更改用户勾选的NR/画质参数。
- 音频补偿、音画软件偏差、被跳过原帧/FG计算、计算完成后过期数。Present/SDK提交与实际屏幕刷新仍分别标注。

普通日志每秒汇总，状态转变立即记录并限频：音频时钟PTS、视频PTS/覆盖范围、同步目标、原因为何进入/退出等待、累计Stop/Reset、补帧准入/恢复、各队列高水位、输入/设置/epoch及后端。日志写入沿已有批量机制，正常路径不强开逐帧刷盘或像素回读。

诊断必须能回答：算了多少原帧，跳过多少增强，算了多少有效补帧，浪费了多少过期结果，声音有没有停过，媒体时间有没有变慢。日志/原片不进入Git。

## 8. 验收矩阵

以下均为实施后的待执行项；本方案编写时没有新增GPU或声学实测。单次测试最多300秒，建议20–60秒稳态样本；启动/显式交互窗口与稳态分开，不抹掉失败。

| 用例 | 必须证明 |
| --- | --- |
| 60fps→2X，容量控制到约110提交/秒 | 声音正常一倍速；预算不足时优先省FG；源PTS完整覆盖真实时间，不能重现55原帧/秒慢播 |
| 30fps原片，NR容量约15帧/秒 | 被选PTS覆盖整秒、间隔接近均匀；显示非只有前半秒；音频不随帧停放 |
| 30/35ms交替及±10ms短波动 | 0额外音频Stop/Reset/PCM欠载；不发生每帧补偿跳变或频繁FG开关 |
| 充足→持续不足→恢复，60秒 | 欠速期间媒体正常推进、队列有界；恢复后回到全帧而不回放积压；日志有明确原因 |
| FG关闭的NR欠速、仅SR、仅基础播放 | 不把全部问题误归因于FG，测真实处理而非理论计数 |
| DLSS2X/3X/4X与XeSS2X | 独立准入/恢复/真实生成验证；XeSS不能用普通Present计数×2作为成功 |
| 暂停seek、负音频PTS、音轨EOS、无音轨/静音、端点恢复 | 无首帧死锁、旧PCM/旧epoch污染、时间倒退、EOS丢尾 |
| 设置修改/失败回滚/resize/全屏/源切换 | 显式重同步次数有界、状态可解释、无悬空引用或旧帧闪回 |
| 合成采集共同输入延迟＋软件30/35ms、80/160/400ms阶跃 | 不重复补偿共同输入延迟；小波动连续，大阶跃仅一次受控重同步；队列不增长 |
| 真实运动、文字、场景切换与15fps采样 | 历史reset/FG恢复无错误跨帧、严重闪烁、旧纹理或假生成计数 |
| NVENC H264/HEVC及图片导出 | 原有帧数/时长/音轨/尾帧/取消检查通过；导出没有任何预览跳帧计数 |

拟定量化门槛：

1. 排除用户明确暂停/seek/设置重建/端点断连，稳态30秒音频媒体进度与墙钟之差不超过100ms，且音频额外Stop/Reset/欠载为0。不能靠循环静音、丢PCM或偷偷放慢声音通过。
2. 文件选帧后实际呈现的PTS持续覆盖主时钟位置，不能欠半段媒体；30→15的15张应分布在整秒。目标110是负载用例，不要求恰好每秒110张。
3. 软件同步误差使用呈现时刻音频PTS与该视频PTS比较。采集若音视频PTS原点不同，先按输入映射统一原点；原点一致后不能再减一次补偿D，否则会重复扣除。补偿量和剩余同步误差分列。拟定P95不超过 `max(35ms, 源帧间隔＋实际音频端点缓冲时长)`，同时报告最大值、斜率及观测点。画面保持到下次显示产生的离散误差另记，不能将15fps天然帧间隔伪装成测量精度1ms。
4. 队列、候选帧、在途GPU资源有固定上限；60秒持续欠速不得产生随时间增长的延迟/内存趋势。具体时钟不确定性和稀疏采样写入报告，不只给平均值。
5. 候选源码改变后执行适用的 `scripts/build.ps1`、integration tests及 `scripts/gates/delivery.ps1`；沿用`run-short-test.ps1`外部超时。既有导出gate保持原判断，针对新预览语义更新旧“过载应该停音”断言时保留新旧A/B证据。

不因本机5070通过就写4060通过。4060应由用户在相同60fps文件与同设置上复验；日志要能独立说明真实处理速率、媒体速度、音频停放与跳帧原因。物理扬声器/屏幕同步与长时间直播稳定性仍需单列，不用软件PTS代替。

## 9. 主要风险与停止条件

- 低处理帧率会损失短暂画面信息，这是正常速度与固定算力下的取舍；不能宣传为“所有帧保留、画质完全不变”。
- 跳原帧频繁reset可能损失NR时序收益，FG重新预热可能抵消节省；出现该问题先固定采样节奏和禁用无效生成，不能无限扩大队列。
- 解码不足、音频源自身断流、驱动故障、一次GPU任务极长阻塞，不承诺靠本策略完全消除；必须与正常欠速分开诊断。
- 不接受新代码只做到音频连续而视频越来越落后，也不接受偏差小但周期性静音。若拟定同步门槛失败，记录原因并修实现，不默默放宽门槛制造通过。
