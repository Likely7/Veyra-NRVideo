## 2.5 DLSS 4X/6X 补帧受限追加审查

用户追加反馈多用户4X/6X受限。不能假设补帧成本恒小：当前 `src/pipeline/EnhanceGraph.cpp:1902` 对4X执行3次、6X执行5次 Evaluate，另有资源转换、状态读取和提交；实际成本须按分辨率、设备、倍率测量。GPU低利用率也可能是输入不足、显示反压或软件拒绝工作。

### 已确认的代码机制

1. `EngineController.cpp:1186` 的计算前拒绝更新 `lastFgRejected100ns`，界面在约1秒内标为受限。该标志不是GPU饱和判据。XeSS走呈现端，不使用此图内预算，必须分别诊断。
2. `EngineController.cpp:1289` 的 Present 服务样本只扣除 allocator 等待，仍包含 DXGI/驱动阻塞；`FgRecoveryBudget::admit` 再将其P95加到预计剩余工作。显示反压可以导致尚未计算的整组FG被拒绝。当前单测甚至明确覆盖“80ms Present导致拒绝”，但只验证样本过期恢复，未覆盖周期性显示阻塞与持续生成。
3. `EnhanceGraph.cpp:1892` 一次决定整组是否执行；拒绝置 `fgHistorySkipped_`。下一次获准会 reset 并执行全部子帧，但 `hasGenerated=false`，再下一对连续获准才可能输出。一次拒绝至少损失本组和随后暖机组的生成机会；交替拒绝/获准可以持续算暖机却没有有效补帧。不能直接删掉必要reset，否则历史错误会变为画面故障。
4. 预算使用最后一个子帧的期限，呈现按每个子帧期限另做过期淘汰（采集容差10ms）。所以“获准计算”不保证3/5个子帧全部赶得上。`LivePairLatency` 当前只允许比旧相位更早，不能超出“一源帧间隔+base成本上限”；需要检查其对较慢FG和6X首子帧是否足够，不能未经测量直接全局增加延迟。
5. 预算的 graph span 是同队列首尾GPU时间戳包络，包含依赖等待，并非各阶段纯执行耗时之和。CPU elapsed 也不等于GPU已完成量：admission前有条件提交点，但最后一段base在admission后才提交。必须拆开执行、依赖、供给空洞和显示等待，不能重复计费或把CPU忙碌当GPU进度。

算式示例（仅模型，不是实机测试）：预算预测12ms、base进度抵扣2ms、剩余期限8ms，容差10ms时，无Present等待需要10ms，可获准；Present P95为17ms时需求变成27ms，被拒绝。它证明等待可触发受限，不证明17ms阻塞必然可以安全忽略；显示吞吐确实不足时仍需有界背压。

### 日志边界与反证

A的11:35:30.863至11:35:34.929，`fgSkippedBeforeEval`始终为9，是累计值，不能把每行9都算成持续新拒绝。11:35:31/32有约121/120fps提交；11:35:33跌至94，epoch100->102、暖机15->21、生成过期3->7，而计算前拒绝未增加。这次下降更符合历史重置/过期，不能全归预算门禁。A的87条节流admission日志均为true，但累计计数证明存在漏采的拒绝事件，现有每秒采样不能还原其当时成本。

### 修复顺序与验收补充

1. 优先记录拒绝事件的原因和分项成本：预算、首/末子帧期限、显示等待、GPU阶段/依赖、来源间隔、倍率、暖机状态。按窗口聚合并保留首个状态转换，避免逐帧大量日志造成干扰。UI区分计算前拒绝、过期、暖机、SDK无效、显示吞吐上限。
2. 将必需计算成本和显示反压分开建模；保留有界显示队列。不能仅把Present项归零，也不能通过关闭预算一律猛算来宣称修复。基于首子帧就绪与后续子帧节奏校准期限，确认同一等待未被重复扣除。
3. 恢复策略必须能完成连续的暖机与有效生成，避免交替拒绝反复暖机；在真实源断点时仍reset。对所有子帧都过期、只有前几个过期和短暂显示阻塞分别验证，不制造假帧或修改FPS计数。
4. 检查单owner同步Present及上一批GPU完成等待是否阻断可安全准备的下一帧；先量化，再在现有资源所有权和有界队列内修复，与5080工作连续性排查共同推进。
5. 增加受控时间线回归：2X/4X/6X，30/59.94/60源，周期性17/33/80ms呈现阻塞，一次拒绝、交替拒绝、连续恢复、样本老化、真实GPU超预算和输入断点。断言有效生成恢复、每类丢帧原因、队列上限及历史正确性，而不是只断言admit返回值。再同参数120秒实机对照，分别报告FG执行耗时、有效生成、显示提交、过期和恢复时间；30/40/50系验收独立记录。

## 3. 施工顺序

### P0：把每次等待和丢帧归属测清

1. 在现有诊断中增加会话内增量：实际来源类型、输入到达、解码完成、图提交/完成、呈现入队、提供方调用开始/返回。绑定 source ID、epoch、revision；统计固定窗口 P50/P95/P99/max，不逐帧刷生产日志。
2. 区分输入 mailbox 覆盖、主动限帧、性能跳过、生成失败、显示淘汰；reset 记录原因与前后源帧身份。
3. 同步状态拆成用户请求、应用等待、提供方调度、实际 sync/tearing flags。提供方生成帧记录全序列间隔，包含批次边界，并解码 SDK 返回码。
4. 利用上一轮已有回调锁等待/复制指标，补齐回调入口/出口、驱动 PTS、协商格式和 allocator；确认诊断不会显著拉低吞吐。

### P1：XeSS 呈现与历史连续性

5080 优先做同输入三组120秒对照：NR only、XeSS4X only、NR+XeSS4X；固定原生4K30、画布和显示模式，排除主动限帧与参数切换。分别测增强图 GPU、XeSS 提供方 GPU、XeLL sleep、媒体 deadline、proxy Present 和最终子帧调度；同步采功率/核心频率/显存/利用率/节流原因，并用共同单调时钟对齐。无5080时本机只验证机制，不能代替该用户功耗验收。

必须用 GPU 时间线或等价可验证的队列证据区分“Present 在等 GPU 执行”和“CPU 等显示导致下一批 GPU 工作未提交”。如果确认后者，优先在现有有界调度器内调整准备/提交顺序，让允许独立的下一源帧准备利用等待时间；保留 XeSS tag->Present 期间同队列资源状态和消费者 fence 合同。不能直接把 Present 搬到另一个线程并同时复用纹理。若涉及独立队列/线程，另列资源所有权和GPU验证矩阵后实施。只在测量证实期限重复时合并等待，不能同时撤掉所有节奏控制或用忙等耗电“稳定功率”。验收目标是减少稳态长帧和异常生成缺口，不是强求瓦数恒定。

1. 基于现有 VSync 改动验证提供方最终 Present；完全关闭仍必须生效。低排队/Reflex 等应用等待不叠到 XeSS 调度器上，界面说明实际生效范围。
