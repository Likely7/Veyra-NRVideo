# 补帧内容节奏：去除重复帧重新设计（2026-10-11）

> 2026-10-12 修正（docs/CONTENT_CADENCE_EXACT_2026-10-12.md）：“采集 60→30”已恢复为按时间戳隔帧（CaptureHalfRate），不再去重；内容模式不再用 64×36 采样点与变化门限，改为整画面逐像素与上一张新画面比较（每个分量都在采集噪声 ±3 级以内才算重复），静止画面按内容节奏保留。下文是 10-11 版本的记录。

## 授权与范围

- 用户：现在的去除重复帧还是软件初期设计；PS5 等游戏锁 30/40 帧、采集卡采 60 帧（延迟比采 30 帧低）时，希望在补帧的“内容节奏”里重新设计去重复帧，兼容各类帧率；原来的 60→30 容易把真实帧也剔除，导致补帧鬼影；不要增加大量计算耗时；用 GTA6 30 帧视频渲染成 60 帧、58 帧来测试。完成后汇报并关机。
- 沿用规则：先存档、开分支，负优化就退回。
- 只改直播类来源（采集卡及其测试回放）的内容节奏处理：重复画面判断、留帧、内容时间戳。不改 NR/SR/FG 模型、呈现策略、默认设置、运行库和驱动。不 merge/push/Release。

## 原来的做法和问题

- “采集 60→30”（`CaptureHalfRate`）：按时间戳每两帧留一帧，代码注释自己写明不识别画面是否重复、不处理不规则节奏。游戏帧没有正好落在这个网格上（卡顿、锁 40 帧、58/59.94 Hz 传输）时，会丢真实帧、留重复帧，补帧就在“跨两步的画面”之间插值（鬼影）或在两张相同画面之间插值（停顿）。
- “自动识别 / 识别 xx fps 内容”：只统计 30/50/60 三种帧率用于显示，并把与上一帧完全相同的帧对应的插帧标为无效；重复帧仍按原时间送显，补帧节奏不均匀。

## 新做法（`include/veyra/engine/ContentDedup.h`）

1. **判断重复**：用采集回调复制每帧时已经取好的 64×36 个亮度点（不读 GPU、不读写合并内存），与“上一张留下的画面”比较。
   - 任一点明显变化（超过噪声门限，干净采集下 1 个点即可）或多数点整体变化（淡入淡出、平移）→ 新画面；
   - 否则是重复画面，在任何 GPU 工作之前丢掉（NR/SR/补帧都不再处理重复帧）。
   - 与“上一张留下的画面”比较，缓慢淡变会累积到门限而不会被一直丢掉；同一画面最长保持 150–250 ms（静止画面偶尔留一帧）。
   - 压缩采集卡的噪声会被学习，门限随之提高；判断不确定时偏向保留。
2. **内容时间戳**：新画面一定出现在“上一个采样之后、这个采样之前”。用最近 48 张新画面的采样时刻做线性回归估计内容周期，预测时间夹在这个时间窗内：
   - 规则内容（30 帧放进 58 Hz、40 帧放进 60 Hz）得到均匀的 33.3/25 ms 间隔，且绝不晚于实际采到的时刻；
   - 连续两次对不上（卡顿、帧率变化）就重新学习，期间使用采样时刻。
3. **各模式**：
   - 采用源时间戳：不变；
   - 自动识别 / 识别 30·50·60 fps：去重 + 内容时间戳（指定帧率在 ±3% 内时直接采用该周期）；
   - 采集 60→30：去重 + 上限 30 帧（同一个两时隙窗口里有新画面就不会留重复帧，跟随游戏的相位）。
- 测试开关 `VEYRA_TEST_CONTENT_DEDUP_LEGACY=1` 恢复旧行为，用于同 EXE A/B。
- 只对能拿到 CPU 画面的来源生效（采集卡、测试回放）；硬件解码的串流/文件仍保持原样。

### 结论

- 30/40 帧内容的 6 组新版回放：约 2,300 张真实画面**没有丢失**，**没有留下重复帧**；58 Hz 下 34.5/17.2 ms 交替的采样被还原成均匀的 33.3 ms，40 帧内容在 60 Hz 下被还原成均匀的 25 ms。
- 旧 60→30 只在内容正好是 59–61 Hz 的一半时正确；58 Hz 时完全不起作用（留下 520 张重复帧），40 帧内容丢了 25% 的真实画面——补帧会在跨两张画面的大步长上插值，就是群里说的鬼影。旧“自动”留下全部重复帧，补帧节奏 16.7 ms 交替。
- 开销：每帧 CPU 判定约 14 µs（P99 ≤ 60 µs），没有 GPU 工作；重复帧在任何 GPU 处理前被丢掉，30 帧内容放 60 Hz 时 NR/SR/补帧的处理量减半。
- 强噪声（重复帧之间每点差异中位数 3 级、最大 26 级，和慢镜头里真实新画面的差异一样大）时无法区分，按设计全部保留，行为等同“采用源时间戳”，不会丢真实帧。

## 未验证与边界

- 只用渲染素材回放验证；没有用真实采集卡 + 锁 30/40 帧的游戏实测，也没有 NS2/PS5 现场确认。群里提到的“不开补帧 60→30 也卡”以及 59.94/60 设置问题属于呈现时钟，另作处理，本次没有改。
- 硬件解码的来源（PS5 Remote Play、Moonlight、Xbox 串流、硬解文件）没有 CPU 画面，不做去重；60→30 对它们仍按时间戳隔帧，与旧版一致。
- 强噪声的压缩/模拟采集无法去重（安全退化为保留）。
- 新会话或设置变化后，前约 0.7 秒在学习内容周期，期间使用采样时刻。
- 64×36 采样点碰不到的极小变化（例如画面中只有几个像素的光标闪动）会被当成重复，最长 150–250 ms 后一定留一帧。
- 测试程序 `veyra_live_presentation_tests` 的 `wmain` 原本就贴着 1 MB 栈上限，本次给它加了 `/STACK:8388608`（只影响测试程序）。测试回放现在可以按 `softwareDecode` 走 CPU 解码（只在测试开关 `captureReplayForTest` 下，UI 不会开启）。
