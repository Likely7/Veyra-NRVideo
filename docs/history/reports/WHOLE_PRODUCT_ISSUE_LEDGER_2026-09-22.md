## 2. DLSS：6X 历史问题没有解决，2X 也不能漏

### D1 / P1：高提交率但呈现不均匀

1.4.3 发布说明本身就写明固定 6X 尚未均匀呈现：原生 4K60、NR 内部 1080、
SR 旁路时，部分近期窗口约 295–303 次提交/秒，仍有约 16.8ms 长间隔。
这不是稳定 360fps，更不是同条件真实超分成绩。

后续同条件、同机器的 30 秒版本对照为：

| 场景 | 1.4.3 提交/s | 当时被测开发版提交/s | 间隔 P99，旧/开发版 |
| --- | ---: | ---: | --- |
| 原生 4K、NR、DLSS 6X | 272.03 | 268.23 | 16.934 / 16.899ms |
| 真 1080p→4K 超分、NR、DLSS 4X | 135.44 | 134.42 | 17.063 / 17.099ms |
| 真 1080p→4K 超分、NR、DLSS 6X | 139.67 | 138.05 | 17.125 / 17.127ms |

原生输入的后段 298 与另一轮全段 268/272 不能拼成“性能退步 30fps”的结论。
但三组结果都不能证明均匀高倍率。60Hz 源帧间隔 16.67ms 正常；
若目标是 360 次均匀输出，输出间隔应接近 2.78ms，频繁出现整段 16.8ms 空档就不正常。
P99 不能单独说明全部观感，还要核对空档频率、真实画面时间和实际显示。

已有证据：一组重负载 DLSS 4X/6X 样本约 132.85/135.93 提交/s，
295/361 组 real-only 与预算拒绝/历史播种相关，生成后过期为 0。
另有完整组 GPU 测量：原生 NR 6X 约 18.07ms、真实超分+NR+6X 约 22.92ms。
这些是当前实现下的串行工作耗时，不是不可优化的硬件下限；
也不能把所有亏损说成“算好了但故意不显示”。

下一步不是再次全局取消预算：

1. 利用已有逐组证据，把长空档分别落到输入缺失、处理晚到、预算拒绝、一次播种、
   生成无效、已就绪未及时呈现。每组只按真实经过计数，防止重复归因。
2. 核对单次恢复是否在连续源上被重复触发、预算是否使用同组正确的 ready fence/期限、
   原帧早呈现是否错误影响下一组状态。已有正确播种修复保留；没有反例就不重写它。
3. 对“生成已有效且及时就绪但漏呈现”只修其具体顺序/状态错误；
   对 GPU 关键路径超预算的组，不用推迟期限、堆帧或减画质制造通过。
4. 使用带已知运动位置的画面核对原帧和各生成帧的时间位置，补齐旧记录留下的
   interpolation-position 验收缺口。纹理像素未被覆盖不等于插值时间正确。

完成门槛：同工况全段长空档和突发比例改善，源覆盖、帧龄、画质不退步；
只有平均提交率上升不接受。不能承诺在当前计算预算下所有机器满 6X。

### D2 / P1：5090 连 2X 不满、低占用

4K P010/60、原生 NR、质量光流的用户日志显示源处理约 56–58fps、
总提交约 106–114fps；预算约 999 接受/1 拒绝，690 有效生成/0 无效，
689 生成呈现/1 过期。质量光流约 5.3ms、NR 约 8.5ms，ready 约 14.7–15.3ms。
因此这份日志不支持“大量生成帧被门禁挡掉”的解释。

已接受 P010/P016 冗余 CPU 上传消除，本机上传中位值约 2.4→0.93–0.98ms，
18 个 GPU 像素指纹相同。仍缺 5090 对应整链路复验；切换重建约 1.618 秒、
约 95 丢源另算，不能混进稳态。
下一步沿输入→上传→光流/增强→生成→呈现找第一处超期，优先 2X 基础连续性，
再上 4/6X。不能因 5090 GPU 平均 60% 就断言全部功能应轻松跑满。

### D3 / P1：30/40 系兼容与持续运行

1.4.1 有用户反馈可用，不能推翻这段历史；但“能创建 Feature/能选 6X”
和“当前版本长时间在所有 30/40 卡均匀 6X”是两项验收。

## 3. XeSS：4X 连续性倒退与果冻/闪烁分开处理

### X1 / P1：重负载连续性确实比 1.4.3 差

同一版本对照：原生 4K+NR+XeSS 4X 两版均约 60 源帧/s；
真 1080p→4K 超分+NR+XeSS 4X，源帧率 58.51→39.84/s，
外层 Present 间隔 P99 30.279→40.921ms；SDK 输出约 96.39→129.79/s。
不能用输出数字上升掩盖源运动覆盖变差。

旧版每 30 秒反复 suppress/resume 27/37 次，部分时间实际没有补帧。
当时比较基线的 XeSSPresenter/Pacing 实现与 1.4.3 相同，外围启停行为不同；
未做完整单提交二分，因此不能说已证明唯一致因提交，也不能恢复偷偷停补帧来冒充修好。
XeSS 最高 4X，没有 6X。XeSS 当时交换链为 2560×1440，DLSS 生成 4K，
这些数据只支持同后端版本比较，不支持两算法性能排名。

### X2 / P1：provider 等待与 GPU 工作交织，低功耗不是空闲证明

同工况旧测：XeSS 2X 源 60、输出 120/s、GPU 91.58%；4X 源 39.84、
输出 129.79/s、GPU 72.73%。诊断关闭 pacing 可到源 51.98、输出 183.61/s、
GPU 94.81%，但突发呈现未通过，不能作为发布方案。

351/351 个保留的首子帧调度入口仍有未完成 fence；入口到 deadline 段
平均 8.465ms/P95 14.300ms，随后等待约 3.815ms。约 8.5ms 包含 GPU 依赖、
队列与唤醒，不能全删，也不能全算 GPU 算法耗时。
另一个 SDK 返回 47.473ms 的样本内含 36.954ms native Present。

未完成的下一步是对具体等待归属做闭环：将该 fence 的 signal 队列、前序提交、
就绪时刻、实际呈现唤醒关联起来，区分图未完成、提供方生成未完成、系统 Present 阻塞、
就绪后调度迟到。没有找到确切错误前，不再做简单拆 owner、换队列或增加并行的实验。

### X3 / P1：已有源时间候选，不是已接受的优化

`VEYRA_TEST_XESS_SOURCE_TIMING` 默认关闭；历史源吞吐约 40→52/s，
持续样本约 52.09/s，但约四分之一输出间隔小于 1ms，偶发约 46ms 空档。
Intel 允许 frameRenderTime=0，不能把默认 0 当 API 违规。
只补这项候选尚缺的完整节奏和图像验收，不包装成新方案重跑吞吐数字；
若不能同时改善连续性、画质和帧龄，不启用。已失败的一组 pending 方案不重试。

### X4 / P1：果冻、拖动掉帧、欠速闪烁没有统一定因

切换能力缓存/XeLL 周期、窗口变换 motion 映射、断点恢复已有局部修复；
合成拖动/缩放回归通过不能证明快速游戏转身无果冻。
下一步固定 NR/SR/光流设置，对同一源对检查 motion、颜色、HDR 基底、映射纹理、
描述符和 provider 实际消费结束，核对欠速与恢复后的图像。
算法运动估计缺陷、颜色跳变、时间位置错乱分别记录；不默认换 AMD 光流，
不靠锐化或默认 NR 防闪滤镜掩盖，不在拖动时关闭生成。

## 5. 施工优先级与禁止重复

1. **第一优先级是 D1/D2/X1–X4/F1。** 现有逐组数据先归类，不再先增加大堆日志。
   同时用 C1 全关断供作为对照，防止把公共链路停顿归给 FG；不能等所有采集/UI 问题
   都结束才处理历史 6X 和 XeSS。
2. **可独立关闭的确定性缺口是 C2/H1。** 以故障注入和合同回归为门槛，
   不宣称它们包办所有闪烁、卡死、变糊。C3 单独做匹配画质对照。
3. **接受任何调度修复前回归其他模块。** 低/高倍率、两后端、原生与真超分、
   SDR/HDR、文件与采集分开；相关生命周期覆盖切换/seek/暂停/拖动/跨屏/退出。
   公共图改动再验截图/导出/字幕/颜色，不能只跑 FG smoke。
4. **功能缺口单列。** 独立降噪、提供方输出限帧、完整 Reflex 有实现前提，
   不作为这轮卡顿根因修复的假承诺。暂缓项维持暂缓。

不再安排：全局取消 admission、扩队列、固定延迟、提高队列优先级、简单拆线程/
owner/逐输出发布、无新关键路径证据的 FG/Enhance 重叠、NVOF/SR overlap、
同组成本估算器、去清屏/光流历史复制/原生光流尺寸直传、XeSS 一组 pending、
Present 间隔反喂 provider、拖动停止生成、自动降档或减画质。
源时间候选只验未完成部分。详情见[实验索引](FG_EXPERIMENT_INDEX_2026-09-21.md)。

每个实现单独存档、固定基线；最小对照无收益就撤回，不用另一处优化遮住本项退步。
GPU 满载不是验收目标，功率稳定也不能替代运动/画面和帧间隔正确。
可消除的软件阻塞没有证据时，报告边界，不通过无限试验承诺硬件必能满倍率。
